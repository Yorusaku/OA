# 企业级类Figma AI设计与应用生成引擎架构设计与实践面试专项突击
## 1 需求背景介绍
在AI重塑软件生产力的今天，设计与开发之间的鸿沟依然是产品迭代的最大瓶颈之一。传统设计工作流中，设计师出图、前端还原的协作模式存在大量重复劳动，一个页面从设计稿到可运行代码往往需要数天时间，而且不同开发者还原度参差不齐，设计一致性难以保障。对于快速迭代的创业团队和中大型企业的产品部门来说，设计到代码的转化效率直接决定了产品上线速度。
妙码设计AI平台正是针对这一痛点打造的AI驱动桌面端D2C设计生成引擎，是一款高专业化的设计智能体。它的核心定位是：让大模型能力深度适配设计行业workflow，从自然语言需求到设计产物再到代码输出全链路智能化，通过多智能体协作自动完成大部分设计生成与还原工作，只把创意决策和最终微调留给人类。
### 1.1 核心目标用户分层
1. 前端开发者：全栈工程师、业务前端、低代码平台开发者。核心痛点是设计还原工作重复琐碎、占用大量业务开发时间，希望通过AI自动完成基础还原，把精力集中在业务逻辑和交互实现上。
2. UI/UX设计师：产品设计师、运营设计师、独立设计师。核心痛点是从0到1出方案慢、改稿频繁、重复性设计多，希望通过AI快速生成多版方案、聚焦创意决策而非像素级调整。
3. 产品经理与创业者：独立开发者、创业团队、产品经理。核心痛点是不会专业设计、找不到设计师、原型制作成本高，希望通过自然语言描述快速产出可用的设计稿和原型，加速需求验证。
4. 设计系统团队：企业设计中台、组件库维护团队。核心痛点是设计规范落地难、各业务线还原度不一致、组件库更新同步成本高，希望通过标准化MCP接入让所有AI工具都遵循同一套设计资产。
### 1.2 垂类设计智能体的业务与技术价值
传统AI设计工具大多只停在单点AI增强（比如一键生成图标、自动配色），没有从全链路重构设计生产流程。本项目作为完整的设计生成智能体，核心价值体现在：
#### 1.2.1 业务价值
- 端到端自动化：用户只需输入自然语言需求，Agent自动完成需求拆解 → 区域规划 → 并行设计生成 → 视觉自验证 → 代码导出全流程，把页面产出周期从「天级」压缩到「分钟级」
- 人机协同最优分工：Agent承担80%重复性劳动（布局生成、样式还原、组件拼装、格式校验），人类只负责最后的20%创意调整和质量确认，真正做到「AI做量 + 人类做质」
- 本地隐私保护：所有设计文档和生成过程都在用户本地完成，不需要上传待解密的产品原型到云端，满足企业级隐私合规要求
- 可编程可调整：AI生成不是终点而是起点，用户随时可以在类Figma编辑器中做精细化调整，兼顾自动化效率和创作灵活性，生成的设计产物完全可编程、可分层、可复用
#### 1.2.2 技术价值
- 验证了Codex CLI本地智能体落地：在真实的设计生成场景中，实现多智能体协作、Harness内核、视觉自验证等复杂智能体架构设计
- 沉淀了MCP标准化接入最佳实践：设计资产通过标准MCP协议对外暴露，一次接入兼容Codex / Claude Code / Cursor等所有MCP客户端，解决N×M集成问题
- 完整工程化链路：覆盖DSL内核设计、编辑器开发、智能体引擎、MCP服务、多端打包及安全流程，是学习AI桌面应用开发的绝佳实战项目

## 3 学习产物
### 3.1 多智能体生成引擎（@miaoma/agent-core）
- 基于Codex CLI的完整多智能体编排体系，包含1个Coordinator协调者 + 5个Collaborator执行者的角色分工体系，支持按区域并行生成设计内容
- 完整的Generation Run状态机实现，覆盖queued → preparing → designing → validating → repairing → completed / failed全生命周期，支持状态持久化与断点恢复
- Codex Provider抽象层，统一封装子进程调用、JSONL事件流解析、Thread会话管理，支持不同AI引擎的可插拔替换
- 实时流式输出能力，规划区域与生成进度实时同步到编辑器，支持光标指示器与增量渲染
### 3.2 设计DSL数据内核（@miaoma/design-schema）
- 基于Zod的完整设计文档数据模型，采用可辨识联合类型设计，支持Frame、Rectangle、Ellipse、Icon、Text五大核心节点类型
- 正交属性拆分设计：布局属性、视觉样式、变换属性分层定义，原子化样式单元自由组合
- 设计变量系统（Design Variables）：颜色、字号、间距、圆角等设计Token统一管理，全局引用保证一致性
- 版本字段与向前兼容设计（documentVersion），支持Schema演进与数据迁移
### 3.3 类Figma可视化编辑器（Electron桌面应用）
- 基于Electron + React 19 + TypeScript + Vite的完整桌面设计编辑器
- 三栏经典布局：左栏图层面板 + 中栏画布编辑区 + 右栏属性配置面板
- 完整画布交互系统：三层坐标变换、命中测试、选择集管理、拖拽移动、缩放平移
- 命令模式 + 不可变数据 + 发布订阅三大编辑器范式，支持历史栈撤销重做
- 注册驱动的属性面板，按节点类型动态渲染属性编辑器，支持批量编辑
### 3.4 MCP设计资产接入服务（@miaoma/mcp）
- 符合Model Context Protocol标准的只读MCP Server，封装5大工具：get_app_state、get_selected_node、get_nodes、get_screenshot、get_assets
- Bridge跨进程桥接层，通过Unix Domain Socket（macOS）与Named Pipe（Windows）实现MCP独立进程与渲染进程的可靠通信
- Sidecar独立可执行文件模式，支持Codex / Claude Code / Cursor等所有MCP客户端启动
- 9种分级错误码体系，超时控制、优雅降级、故障隔离等可靠性保障机制
- 资产目录化机制：自动提取设计文档中的图片资源，通过miaoma-asset://URI协议统一引用
### 3.5 Visual Harness视觉验证系统
- Schema结构校验 + 多模态视觉验证的双重质量保障体系
- 七大检查维度：布局对齐、层级关系、文本可读性、色彩对比度、组件完整性、变量一致性、边界溢出
- 自动修复闭环：发现问题 → 定位节点 → 精准修复 → 回归验证，最多重试2次防止无限循环
- 最小改动原则：每次修复只修改指定节点，不影响其他区域，控制变更范围
- 结构化Visual Issue描述：精确到节点ID的问题定位，修复目标明确可追溯
### 3.6 生成编排器（Orchestrator）
端到端生成流程的总指挥，负责将用户的自然语言需求拆解为可执行的生成任务，协调多智能体并行产出，并串联视觉验证闭环，最终交付完整可用的设计文档，是连接用户输入与设计产出的核心调度层。
- 五阶段生成流水线：需求解析 → 区域规划 → 并行生成 → 文档组装 → 验证交付，每个阶段有明确的输入输出与验收标准，流水线式推进保证生成过程可控可追溯
- Coordinator智能任务拆分：根据页面需求自动识别功能区域，按导航栏、Hero区、功能模块、页脚等语义单元划分生成边界，每个区域分配独立的Collaborator并行处理，拆分粒度兼顾并行效率与上下文完整性
- 并发调度与资源控制：默认最多5个Agent并行执行，通过MIAOMA_MAX_PARALLEL_COLLABORATORS环境变量动态调整，采用自适应机制控制并发上限，避免资源耗尽导致整体性能下降
- Visual Harness验证闭环集成：生成完成后自动调用Harness执行视觉自验证，七大维度逐项排查；验证不通过则触发修复循环，最多重试2次，在质量保障与执行效率之间取得平衡
- 统一事件总线与状态分发：生成过程中的所有状态变更、进度更新、错误信息、流式增量通过事件系统统一分发，前端编辑器实时订阅并渲染，支持生成过程可视化与随时中断
- 乐观锁版本控制：多Agent并发写入同一文档时，通过revision版本号实现乐观锁并发控制，检测到冲突时自动合并或重试，保障最终文档数据一致性
## 4 技术选型
### 4.1 整体架构分层设计
本项目采用经典的四层分层架构，每层职责清晰，依赖方向明确，符合单一职责原则与单向依赖原则：
|分层|职责范围|核心技术选型|设计思想|
| ---- | ---- | ---- | ---- |
|编辑器内核层|画布渲染、图层管理、DSL数据模型、交互状态管理|Canvas + React + Zod + Kiwi Schema|命令模式、不可变数据、发布订阅三大范式|
|Agent生成层|Orchestrator编排器、多智能体协作、Visual Harness验证|Codex CLI + Zod Schema + 多模态模型|规划执行分离、契约驱动、自验证闭环|
|MCP接入层|标准化工具接口、跨进程桥接、Sidecar独立进程|@modelcontextprotocol/sock + net.Socket|标准化协议解耦、一次接入多Agent兼容|
|多端交付层|桌面应用、打包分发、安全加固|Electron + Electron Forge + Fuses|跨平台一次开发多端交付、纵深防御安全体系|
### 4.2 详细技术选型说明
#### 4.2.1 工程与包管理
- 包管理器：pnpm + workspace
硬链接共享依赖节省磁盘空间，安装速度快，Monorepo原生支持良好；symlink严格模式防止幽灵依赖，保证依赖声明的准确性
- Monorepo架构：pnpm workspace
为什么选Monorepo：核心引擎和桌面应用放在同一仓库，版本对齐方便，前端模块修改一次性提交，文档代码同步维护；分层原则：packages放可复用核心库（传输器、无UI依赖），apps放应用入口（依赖packages），依赖从下往上，严格单向不循环
#### 4.2.2 桌面端框架
- 应用框架：Electron
对比选型：vs Tauri — Electron生态更成熟、Node.js原生支持更好，本项目依赖Sidecar子进程和本地Socket能力，Electron的Node环境更友好；vs 原生开发 — Electron复用前端技术栈，一人全栈可以搞定，开发效率高。满足当前项目阶段需求，安全模型：主进程拥有系统权限，渲染进程沙箱隔离，预加载脚本桥接受控API，遵循最小权限原则
- 构建工具：Vite（渲染进程）+ Electron Forge（打包分发）
Vite热更新快、开发体验好，支持main / preload / renderer三个入口独立构建；Electron Forge一站式处理打包、签名、公证、发布，支持Mac生态完善，减少配置工作量
#### 4.2.3 前端与编辑器
- 前端框架：React 19 + TypeScript
React 19带来新的并发特性和Hooks优化，适合编辑器复杂状态管理场景；TypeScript提供静态类型检查，配合Zod做运行时校验，双重保障类型安全
- 样式体系：TailwindCSS 4.0
CSS-in-JS渲染，编译后体积更小，原子类CSS开发效率高，与设计变量系统天然契合
- 画布渲染：Canvas 2D
相比DOM渲染，Canvas在大量图层场景下性能更优，支持精确的像素级控制，适合专业设计工具场景；分层渲染优化重绘范围，提升交互流畅度
#### 4.2.4 AI与智能体
- AI引擎：Codex CLI
核心优势：本地沙箱环境拥有文件系统访问能力、Thread持久化支持长任务、MCP原生支持配置即用、内置Harness规划执行能力。对比：直接调用OpenAI API：API无本地环境、无状态管理、MCP需要自己实现，适合纯云端场景；量：CLI适合本地设计工具这种需要本地文件操作的场景
- 多智能体架构：Coordinator + Collaborator模式
Coordinator负责任务拆分和结果汇总，Collaborator负责具体区域的设计生成，按区域并行执行提升生成速度。对比单Agent：多Agent并行生成速度更快，但需要解决一致性控制和冲突合并问题
- 数据校验与结构化：Zod
一处定义多处复用：Zod Schema定义一次，同时获得TypeScript类型推导（编译时）+ 运行时校验 + AI结构化输出约束，三个场景用同一份定义
- 结构化输出方案：JSON Schema注入 + Zod校验 + 自动重试
为什么选这个方案：相比纯Prompt约束，Schema注入格式稳定性高很多；Zod做最后一层兜底校验，失败自动重试，生产级可靠性有保障
#### 4.2.5 MCP协议层
- 协议标准：Model Context Protocol
对比Function Calling：Function Calling是厂商绑定的API能力，MCP是开放协议，工具与模型完全解耦，支持跨模型跨语言，有完整的工具发现、资源、提示等能力。类比USB-C，一次接入所有设备通用
- 传输方式：Stdio + 本地Socket桥接
Stdio是MCP标准传输方式，简单可靠，所有MCP客户端都支持；本地Socket桥接解决MCP独立进程与渲染进程的通信问题，跨平台分别用Unix Domain Socket和Windows Named Pipe
- 部署模式：Sidecar独立二进制
进程隔离：MCP Server崩溃不影响主应用；独立分发：Codex等客户端可以直接启动二进制；安全边界：符合安全设计原则，权限分离清晰
#### 4.2.6 设计DSL与数据模型
- Schema定义：Zod可辨识联合
通过type字段区分Frame / rectangle / ellipse / icon / text五大核心节点类型，每种节点有独立的属性集，类型收窄精确，扩展性好，新增节点类型不影响现有逻辑。一处定义同时获得TypeScript类型推导、运行时校验、AI结构化输出约束三重价值
- 设计变量：Design Variables
统一管理颜色、字号、间距、圆角等设计Token，全局引用保证一致性，是AI多Agent并行生成时保持风格统一的基础保障
- 存储格式：JSON文档
调试友好、Git可对比，不需要特殊数据库，简单够用；配合revision版本号实现乐观锁并发控制，文档结构扁平清晰，version + fileToken + variables + children四层，易于序列化与传输
- 正交属性拆分
布局属性、视觉属性、交互属性正交拆分，每种属性独立演化互不干扰。填充、描边、阴影等视觉属性以数组形式支持多层叠加，既符合设计工具的行业惯例，也为后续扩展预留了空间
## 5 项目架构
### 5.1 miaoma-agent-core（智能体核心引擎）
简介：项目的AI大脑，负责多智能体编排、任务调度、状态管理、质量把关，是整个生成能力的核心引擎。
- Coordinator协调者：总控，负责任务拆解、区域划分、结果汇总、质量把关，接收用户自然语言需求，拆解为多个独立的生成任务，分配给不同的Collaborator并行执行
- Collaborator执行者：5个并行工作的子Agent，每个负责一个具体区域的设计生成，角色命名采用科学家体系（Newton、Tesla、Maxwell、Curie、Faraday），各自独立工作互不干扰
- Codex Provider抽象层：统一封装Codex CLI的子进程调用、JSONL事件流解析、Thread会话管理、MCP配置加载。Provider模式实现与具体AI引擎的解耦，未来可扩展其他引擎
- Generation Run状态机：管理生成任务的完整生命周期，queued → preparing → designing → validating → repairing → completed / failed / cancelled，状态持久化支持断点恢复与历史回溯
- 并发控制：MIAOMA_MAX_PARALLEL_COLLABORATORS默认5个并行，可动态调整，防止资源耗尽
### 5.2 miaoma-design-schema（设计DSL数据内核）
简介：项目的统一数据协议标准，一处定义多处复用，同时作为TypeScript类型、运行时校验、AI输出约束。自洽文档的单一事实来源。
- 可辨识联合类型系统：通过type字段区分Frame、Rectangle、Ellipse、Icon、Text五大核心节点类型，每种节点有独立的属性集，类型收窄精确，扩展性强
- 正交属性拆分：布局属性（x/y/width/height）、视觉样式（fill/stroke/shadow）、变换属性（rotation/scale）分层定义，原子化样式单元自由组合，避免重复爆炸
- Design Variables设计变量：colors、typography、spacing、radii四大类设计Token统一管理，全局引用保证一致性，是多Agent并行生成时风格统一的基础保障
- MiaomaDesignDocument根模型：version + fileToken + variables + children四层结构，带版本号支持向前兼容与数据迁移
### 5.3 miaoma-mcp（MCP设计资产接入服务）
简介：设计资产的标准化出口，通过MCP协议将编辑器内部的设计数据暴露给外部AI Agent，一次接入兼容所有MCP客户端。
- MCP Server层：基于@modelcontextprotocol/sdk构建标准MCP Server，注册5个只读工具，所有工具标注READ_ONLY_ANNOTATIONS（readOnly / idempotent / destructiveHint / openWorldHint），帮助Agent理解工具语义，优化调度策略
- Bridge桥接层：TCP / Unix Socket本地桥接，MCP Server独立进程通过本地Socket与Electron主进程通信，单次请求-响应模式，10秒超时，6种9级分级错误码
- Sidecar独立进程：打包为独立可执行文件，Codex / Claude Code等客户端可直接启动，通过--bridge-endpoint参数传入桥接地址，与主应用建立连接
- 资产目录化：递归遍历节点树提取fill / stroke中的图片资产，替换为miaoma-asset://URI协议，SHA256生成assetId去重
- 混合内容返回：get_screenshot和get_assets返回text + image混合内容，元信息 + base64图片一起返回，Agent同时获得结构化数据和视觉参考
### 5.4 miaoma-design-generation（生成编排器）
简介：生成流程的总调度，负责将输入需求翻译为可执行的完整流水线，协调各个子系统协同工作。
- Orchestrator编排器：五阶段流水线 — 需求解析 → 区域规划 → 并行生成 → 文档组装 → 验证交付。统一调度Coordinator、Collaborator、Harness各模块
- Visual Harness视觉验证：validate（诊断问题）→ repair（精准修复）→ run（执行完整循环）三方法，七大检查维度，最多2次修复重试，最小改动原则控制变更范围
- 文档组装器：将多个Collaborator的生成结果合并为完整设计文档，乐观锁revision控制并发写入，防止冲突
- 事件系统：统一事件总线，生成进度、状态变更、错误信息统一分发，前端实时订阅展示
### 5.5 apps/desktop（Electron桌面应用）
简介：用户直接使用的桌面端产品，基于Electron构建，提供完整的可视化编辑体验和AI生成交互界面。
- 三层进程架构：主进程（窗口管理、文件系统、Sidecar桥接）+ 预加载脚本（contextBridge安全桥接）+ 渲染进程（React UI、编辑器、画布渲染），严格遵循最小权限原则
- 三入口构建：VitePlugin配置main / preload / renderer三个入口独立构建，各自的依赖和构建优化互不干扰
- 编辑器三栏布局：左栏图层面板（树形图层管理）+ 中栏画布编辑区（Canvas渲染 + 交互系统）+ 右栏属性面板（注册驱动的动态属性编辑器）
- MCP运行时：主进程启动Bridge Server，管理Sidecar生命周期，截图捕获、资产读取、节点查询等能力通过IPC通道提供给MCP层
- extraResource原生资源：schemas目录 + miaoma-mcp/bin目录作为额外资源打包，不打进ASAR包，运行时通过process.resourcesPath动态解析路径

- Electron CI/CD构建体系搭建：能独立搭建多平台构建流水线，理解package与make的分层职责；掌握Fuses安全加固、代码签名、公证、自动更新的完整分发链路，具备纵深防御的安全设计思维
## 8 面试高频问题与回答思路
### 8.1 协议原理类
#### 问题1：MCP和Function Calling有什么区别？为什么不直接用Function Calling？
回答思路：
- 定位不同：Function Calling是某个模型厂商的API能力，绑定特定模型；MCP是开放协议，工具与模型完全解耦，一套工具所有支持MCP的Agent都能用
- 能力范围不同：Function Calling只有工具调用；MCP有三大能力 — Tools（工具调用）、Resources（资源读取）、Prompts（提示模板），能力更完整
- 部署形态不同：Function Calling通常在服务端实现；MCP支持Stdio本地进程模式，可以直接操作本地文件系统，适合桌面端场景
- 生态价值不同：MCP解决N×M集成问题，N个工具接入一次，M个Agent都能用，类似USB-C接口的标准化价值
- 元信息更丰富：MCP的Tool Annotations四元组（readOnly / idempotent / destructiveHint / openWorldHint）帮助Agent理解工具语义，优化调度策略
#### 问题2：你们的MCP为什么做成只读的？开放写入有什么风险？
回答思路：
- 安全优先原则：设计文档是用户核心资产，写入操作可能导致不可逆的数据丢失，只读模式从协议层杜绝风险
- 一致性风险：多Agent并发写入容易产生冲突和数据不一致，编辑器本身有完整的交互体系，不需要通过MCP绕过
- 故障隔离：MCP Server崩溃或异常不会影响文档数据，只读模式故障影响范围可控
- Agent心智负担：只读工具Agent不需要考虑副作用，调用更安全；写入工具需要完整的事务和回滚机制，复杂度高很多
- 适用场景：当前阶段MCP主要用于设计还原、代码生成等读取场景，写入能力可以后续按需开放，遵循最小权限原则
### 8.2 架构设计类
#### 问题3：为什么用Coordinator + Collaborator多智能体架构，而不是单Agent生成？
回答思路：
- 并行提速：单Agent串行生成整页慢，按区域拆分后5个Agent并行，生成速度理论提升4-5倍
- 聚焦聚焦：Coordinator只做规划和汇总，不碰具体生成；每个Collaborator只负责自己的区域，上下文更聚焦，生成质量更高
- 容错性更好：某个区域生成失败不影响其他区域，可以单独重试失败部分，不需要整页重来
- 可扩展性强：新增专家角色（比如专门做排版的、专门做配色的）只需要加新的Collaborator类型，不影响主流程
- trade-off：多Agent带来一致性挑战的复杂度 — 风格统一、布局对齐、跨区域元素协调需要额外机制解决，所以引入了Design Variables和Schema约束来保障一致性
#### 问题4：Harness内核的设计思路是什么？为什么需要记忆、规划、实施分层？
回答思路：
- 记忆层：持久化历史会话和生成记录，Agent可以基于上下文继续工作，不会每次都从零开始。类比程序员的项目记忆，知道之前做了什么、为什么这么做
- 规划层：任务拆解和步骤编排，大任务拆成可执行的小步骤，每一步有明确的输入输出和验收标准，避免Agent想到哪做到哪，提高生成的可控性
- 实施层：具体的生成执行，分片生成 + 文档组装，按规划的步骤一步步落地。和规划分离后，规划可以调整，实施只负责执行
- 验证层：自检校验闭环，生成完自动检查，发现问题自动修复，不需要人工介入。保障产出质量的最后一道防线
- 分层价值：每一层职责单一，可以独立优化和替换。比如记忆层可以扩展组件库记忆、风格记忆；验证层可以增加更多检查维度
#### 问题5：为什么需要Bridge层？MCP Server直接和渲染进程通信不行吗？
回答思路：
- 进程隔离：MCP Server是独立的Sidecar进程，渲染进程在Electron的沙箱环境里，两者不能直接调用，需要通过IPC桥接
- 安全边界：渲染进程权限受限，不能直接访问本地Socket；Bridge层在主进程运行，拥有系统权限，可以创建和管理Socket连接
- 跨平台适配：macOS用Unix Domain Socket，Windows用Named Pipe，Bridge层统一封装平台差异，上层MCP Server不需要关心
- 可靠性保障：超时控制、重试机制、错误分级、优雅降级都在Bridge层统一处理，MCP Server只关注业务逻辑
- 生命周期管理：Bridge Server随主应用启动和关闭，管理所有连接的MCP客户端，统一处理连接和断开
### 8.3 技术选型类
#### 问题6：为什么选择Codex CLI而不是直接调用OpenAI API？
回答思路：
- 本地沙箱能力：Codex CLI运行在本地沙箱里，有完整的文件系统访问能力，可以直接读写本地设计文档，这是纯云端API做不到的
- 状态持久化：CLI内置Thread持久化机制，长任务可以断点续跑，历史会话自动保存；API是无状态的，会话管理需要自己做
- MCP原生支持：CLI原生支持MCP配置，只需要写个JSON配置就能接入，不需要自己实现MCP客户端
- Harness原生内置：CLI内置Harness规划执行能力，记忆、规划、实施三层架构开箱即用，API需要自己从零搭
- trade-off：CLI是子进程模式，启动有开销，资源占用比纯API调用高；但对于本地设计工具这种需要操作文件的场景，CLI的能力增益远大于成本
#### 问题7：为什么用Zod定义Schema，而不是JSON Schema或者TypeScript interface？
回答思路：
- 一处定义，多处复用：Zod Schema定义一次，同时获得TypeScript类型推导（编译时）+ 运行时校验 + AI结构化输出约束（可以转成JSON Schema注入），三个场景用同一份定义
- 运行时校验：TypeScript interface只在编译时生效，运行时没有任何保障；AI生成的数据必须做运行时校验，Zod正好满足
- 组合性强：Zod的object、union、array可以自由嵌套组合，定义复杂的DSL数据模型很方便，可辨识联合类型原生支持
- 错误信息友好：Zod校验失败返回结构化的错误信息，包含哪个字段、什么问题，可以直接用于诊断和修复提示
- 生态兼容：Zod可以很方便地转换成JSON Schema，喂给大模型做结构化输出约束，和AI场景天然契合
#### 问题8：Sidecar为什么要打成独立二进制，而不是直接在主进程里跑MCP Server？
回答思路：
- 进程隔离：MCP Server崩溃不会拖垮主应用，故障隔离。Codex启动的MCP进程和编辑器主进程完全独立，互不影响
- 独立分发：Sidecar是独立可执行文件，Codex、Claude Code、Cursor等任何MCP客户端都可以直接启动，不需要依赖编辑器的编辑器运行
- 权限分离：MCP Server只需要和Bridge通信的权限，不需要主进程的全部系统权限，符合最小权限原则，安全边界更清晰
- 语言无关：Sidecar可以用任何语言写，只要遵循MCP协议就行。当前用TypeScript打包，未来可以换Rust重写性能敏感部分，主应用不需要改
- 为什么不打进ASAR：ASAR是只读归档，Sidecar需要作为可执行文件运行，而且不同平台的二进制都不一样，必须放在extraResource里单独处理
### 8.4 质量保障类
#### 问题9：AI生成的结果质量怎么保障？怎么防止生成的东西乱七八糟？
回答思路：
- 第一层：Schema契约约束：所有生成输出必须符合Zod Schema，结构不对直接重试，从格式层面先卡一道。这是最基础也是性价比最高的保障
- 第二层：领域规则约束：DSL节点类型、属性范围、设计变量都是预定义的，AI只能在允许的范围内选择，不能凭空创造不存在的属性和值
- 第三层：视觉自验证：生成完成后，用多模态模型做视觉检查，七大维度（布局、层级、文本、色彩、组件、变量、溢出）逐项排查，发现问题自动修复
- 第四层：最小改动修复：修复阶段只改有问题的节点，不碰其他区域，控制变更范围，防止修复引入新问题
- 第五层：重试上限：修复最多2次，防止无限循环。修不好就标记出来交给人处理，AI不硬撑
- 核心理念：AI生成不可能100%正确，关键是建立多层防御体系，把错误率降到可接受的范围，同时保证错误可发现、可追溯、可修复
#### 问题10：多Agent并行生成，怎么保证风格和布局的一致性？
回答思路：
- Design Variables统一设计Token：颜色、字号、间距、圆角全部是设计变量，每个Agent都引用同一套变量集，从源头保证风格统一
- Schema契约统一数据结构：所有Agent输出都遵循同一个DSL Schema，节点类型、属性命名、数据格式完全一致，不会出现五花八门的结构
- Coordinator统一规划：Coordinator先做整体布局规划，划定每个区域的位置和尺寸，Collaborator只在自己的范围内生成，不会出现区域重叠或错位
- 全局样式规范注入：每个Agent的System Prompt里都注入统一的设计规范和风格要求，生成前先对齐标准
- 最终汇总校验：所有区域生成完成后，Coordinator做整体一致性检查，发现不一致的地方统一调整，最后再输出
### 8.5 工程实践类
#### 问题11：Electron应用怎么打包原生二进制资源？有哪些坑？
回答思路：
- extraResource机制：通过Forge配置extraResource，把Sidecar二进制、schemas目录等原生资源打进包应用，这些资源不打进ASAR，放在Resources目录下
- 路径动态解析：开发环境用项目相对路径，打包后用process.resourcesPath拼接，不能写死路径，通过环境变量或运行时判断区分开发与生产
- 跨平台差异：macOS和Windows的Sidecar二进制是不同的文件，打包时要根据目标平台只打包对应的版本，不能混在一起
- 执行权限问题：macOS下打包后的二进制可能丢失执行权限，需要在打包脚本里chmod +x，或者用Maker的后处理钩子修复
- 为什么不打进ASAR：ASAR是虚拟文件系统，不能直接执行二进制；而且ASAR是只读的，运行时不能修改，原生可执行文件必须放外面
#### 问题12：Monorepo怎么划分包的边界？怎么避免循环依赖？
回答思路：
- 按业务域分层：packages放纯逻辑的核心库（schema、agent-core、mcp、generation），不依赖UI；apps放应用入口（desktop、server），依赖packages。依赖方向从下往上，核心库不依赖应用
- 单一职责原则：每个包只做一件事，schema只管数据模型，agent-core只管智能体编排，mcp只管协议接入。职责清晰边界就好划
- 单向依赖原则：上层可以依赖下层，下层不能依赖上层。核心包之间也有依赖顺序，比如schema是最底层，所有人都可以依赖它；但schema不能依赖agent-core
- pnpm严格模式：开启symlink严格模式，防止幽灵依赖，每个包必须显式声明自己的依赖，不能偷偷用别的包的传递依赖
- 公共抽象下沉：如果两个包需要共享某类工具，不要互相依赖，把公共部分下沉到更底层的公共包里，双方都依赖底层，避免循环
