# 数字化协同审批平台 副本

# 1 数字化协同审批平台

## 1\.1 项目描述

该项目是一个面向中大型企业审批场景的前端主导型智能协同审批平台原型，核心目标不是继续为不同单据和不同角色堆叠页面，而是把审批系统从“页面硬编码”演进为“协议驱动 \+ 引擎渲染 \+ 状态可追踪”的平台化交付模式。项目聚焦审批规则频繁变化、流程协同复杂、单据处理低效、制度复核依赖人工经验等场景，围绕“动态表单 \+ 流程引擎 \+ 审批治理”的主线建设，并在此基础上接入 AI 审批建议与制度知识库，形成可演进的智能增强层。

从项目定位上看，它不是若干审批页面的集合，也不是以 AI 为主语的自动化审批系统，而是把审批领域里真正具备复用价值的能力沉淀出来，包括表单协议层、流程定义层、节点权限层、审批任务模型、自动治理机制、流程版本治理、审计追踪，以及附着在审批上下文之上的 AI 辅助判断链路。最终形成的是“审批执行主链路 \+ 制度复核支撑 \+ AI 辅助建议”的完整闭环，既能体现复杂中后台平台能力，也能体现智能增强能力，但 AI 始终停留在 Human\-in\-the\-Loop 的辅助层，不越过真实审批边界。

## 1\.2 项目技术栈

Vue3 \+ TypeScript \+ Vite \+ Pinia \+ TanStack Vue Query \+ form\-create \+ LogicFlow \+ Tailwind CSS \+ Element Plus \+ Fastify \+ PostgreSQL \+ Qdrant \+ 火山方舟 Ark

## 1\.3 项目职责

- 动态表单：负责引入 form\-create 搭建 JSON 驱动表单渲染与校验链路，替代按单据类型硬编码页面的开发方式，提升复杂审批单据接入效率与后续规则变更的可维护性。

- 协议适配：负责封装表单 Schema 适配层，完成设计器规则到内部表单协议的转换，统一字段属性、组件映射、校验逻辑与渲染入口，隔离第三方规则结构对业务页面的直接影响。

- 流程编排：参与审批流程可视化重构，基于 LogicFlow 完成节点、连线、事件与流程定义之间的映射和编辑能力建设，支撑流程配置的可视化、可回填与可执行。

- 流表联动：结合审批节点上下文、任务状态与字段权限，动态控制表单读写、隐显、必填和操作状态，实现审批详情视图的自适应渲染。

- 审批闭环：参与审批域核心链路建设，完善发起、审批、转交、加签、催办、撤回与取消等能力，打通待办、详情、通知、统计与轨迹联动。

- 自动治理：参与代理审批、SLA 自动升级、任务责任归属与当前处理人拆分等机制设计，保证转交、代理、超时升级等复杂场景下列表、详情、通知和统计口径一致。

- 流程治理：主导流程版本治理与审计闭环建设，实现发布、回滚、影响分析、版本历史可视化，并将关键操作统一接入审计日志模型。

- 规范沉淀：沉淀表单协议、流程节点配置、共享契约与组合式能力边界，统一审批场景接入方式，降低后续维护、扩展与联调成本。

- AI 增强：参与审批详情页 AI 建议卡片接入，设计 Human\-in\-the\-Loop 置信度分流、流式理由输出与 manual\_review 降级策略，确保 AI 只做辅助判断，不越过真实审批边界。

- 知识库建设：参与制度知识库链路落地，打通 TXT / Markdown / PDF 文档上传、前端文本提取、分块、检索问答与引用来源展示，支撑审批场景下的制度复核。

# 2 技术选型

## 2\.1 工程与质量基建 \(Infrastructure \& QA\)

项目的地基，决定了开发体验、协作效率与持续交付能力。

- 构建与开发环境：采用 Vite 7\.x \+ pnpm 10\.x \+ Turborepo 2\.x 的 Monorepo 架构，保障高频业务迭代效率，同时让 web、bff、contracts、ai\-utils 等模块能够在统一仓库中协同演进。

- 开发语言：TypeScript 5\.9，严格执行静态类型规范，确保表单 Schema、流程定义、审批任务模型、AI 结构化结果与知识库契约在前后端之间具备稳定一致的数据边界。

- 质量保障：引入 Vitest 搭建单元测试防线，并通过 Playwright 补齐关键交互路径验证；测试重点覆盖表单适配、审批治理、会签或签策略、流程版本治理、审计日志、AI 降级与知识库检索等核心链路，保障引擎层能力的稳定性。

## 2\.2 应用核心架构 \(Core Application Architecture\)

项目的骨架，决定了应用的运行机制与数据流向。

- 前端框架：Vue 3\.5 \(Composition API\)，采用 `<script setup>` 与组合式模式，将审批详情派生、节点权限控制、任务状态计算、AI 建议状态机等复杂逻辑进行解耦与复用，突出前端在平台层的承载能力。

- 服务端状态：全面引入 `@tanstack/vue-query` 接管后端 API 请求，利用其 SWR 机制实现审批列表、详情、通知、知识库数据的缓存、请求去重、失效刷新与多页面联动。

- 客户端状态：Pinia 作为全局状态中心，集中管理用户信息、菜单权限、筛选条件、当前视图状态与审批域共享状态，保证业务交互的一致性与可维护性。

- 路由管理：Vue\-Router 4\.x，负责 SPA 单页应用的路由分发、权限守卫与模块导航，支撑审批中心、流程设计、知识库、系统日志等模块化组织。

- 组合式基建：VueUse 用于沉淀长列表渲染、视口侦测、状态副作用收口等底层交互能力，降低业务组件中重复处理响应式细节的成本。

## 2\.3 核心业务引擎 \(Core Engines\)

项目的肌肉，支撑起平台型审批系统的复杂业务场景。

- 动态表单与页面配置：form\-create 负责基于 JSON 规则驱动动态表单生成，结合 Element Plus 落地复杂字段联动、校验、只读禁用与运行时权限注入，支撑“同一张单据在不同节点呈现不同视图”的能力。

- 流程编排引擎：LogicFlow 负责审批流程图的可视化编排、节点配置、连线校验与流程定义编辑，支撑画布交互模型与审批领域模型之间的双向映射。

- AI 与检索基础能力：自建 `@oa/ai-utils` \+ 火山方舟 Ark \+ Qdrant，封装 LLM 调用、Embedding、文本分块、向量写入与检索能力，但其定位是审批平台的增强型基础设施，而不是整套系统的核心骨架。

## 2\.4 可视分析与单据生态 \(Visual \& Document\)

项目的皮肤，决定了用户的视觉体验与文档处理能力。

- 原子化样式：Tailwind CSS 配合 Element Plus 落地 Utility\-First 理念，统一业务页面的排版、状态色和布局节奏，提升中后台界面的实现效率与一致性。

- 数据可视化：ECharts 承载工作台统计、审批分布、节点流转数据与业务报表等图表渲染，增强审批系统的管理视角与数据表达能力。

- 文档与表格引擎：xlsx \+ pdfjs\-dist \+ comlink \+ Web Worker 承担 Excel 导入导出、字段映射、PDF 预览与 PDF 文本提取等重计算任务，减少主线程阻塞。

- 单据与附件协同：通过统一文档处理链路承接审批附件预览、制度类 PDF 文本抽取、报表导出与资料归档场景，减少不同单据类型下的重复实现。

## 2\.5 工程化与质量保障 \(Engineering, Quality \& DevOps\)

项目的保障，确保代码规范、协作效率与交付稳定性。

- Lint 规范体系：ESLint \+ Prettier \+ 共享配置包，统一团队代码风格规范与质量底线，降低多人协作时的风格分歧与维护摩擦。

- Monorepo 协同：pnpm workspace \+ Turborepo 统一管理 web、bff、contracts、ai\-utils、utils 等模块，使前端、BFF 与共享契约能够同步演进，减少跨模块联调成本。

- 测试金字塔：Vitest 覆盖核心 Utils、Composables、服务层与 AI / 知识库链路；Playwright 覆盖审批发起、待办处理、代理审批、升级流转等关键交互路径。

- CI/CD 门禁：GitHub Actions 自动化流水线，PR 触发 lint \+ typecheck \+ test \+ build 四项强制检查，确保功能演进过程中的持续可交付性与回归可控性。

# 3 系统架构设计

## 3\.1 宏观架构策略

### 3\.1\.1 架构定位

考虑到中大型企业审批规则频繁变化、单据类型持续扩展、流程协同链路复杂以及小团队维护成本有限，项目在业务交付层面采用前端主导 \+ BFF 支撑的模块化单体架构。核心目标不是为每类审批单独开发页面，而是围绕动态表单、可视化流程编排、审批闭环治理和节点权限控制，构建一套可持续复用、可持续演进的平台型审批原型。

从架构叙事上看，前端不再只是消费接口、渲染页面的薄壳，而是承担了表单协议适配、节点态渲染、审批视图编排、流程画布交互、任务状态承载等核心职责；BFF 则作为审批上下文治理、数据存储协调、服务端规则收口、AI 服务接入与审计追踪的后端支撑层。AI 能力附着在审批上下文之后进入链路，作为辅助层提供建议，不改变主链路的责任归属和动作边界。

### 3\.1\.2 引擎化建设思路

针对传统 OA 场景中表单硬编码、流程频繁变更、联动规则分散的问题，项目将前端实现重点从页面开发转向引擎能力建设。业务侧主要通过表单 Schema、流程定义和节点配置驱动界面渲染与审批流转，前端负责协议解析、状态适配和交互承载，BFF 负责审批上下文组装、结构化服务与存储支撑，从而降低复杂审批单据的接入与变更成本。

换句话说，系统演进的关键不再是“多写几个页面”，而是“能否用统一协议承载更多单据类型、节点规则和审批场景”。项目中动态表单、流程定义、节点权限、任务模型、自动治理和共享契约构成了平台主骨架；AI 建议和制度知识库则附着在既有审批上下文之上，服务复杂场景下的解释与复核，而不是替代平台主线。

### 3\.1\.3 重计算前置策略

针对财务报表导入导出、电子单据预览、PDF 文本提取等重交互场景，项目将部分高频重计算能力前置到前端，结合 Web Worker 承担 Excel 解析、数据映射、PDF 文本抽取与预览等任务，减少主线程阻塞，提升弱网和大体量数据场景下的可用性与响应速度。

这一策略也服务于知识库链路：制度类 PDF 在前端先完成文本提取，再以 JSON 文本形式发送到 BFF，既减少后端接入复杂度，也让文档处理路径在审批附件预览和制度知识库场景中尽量复用。这里体现的重点不是“做了 AI”，而是前端把重计算能力、文档处理能力和平台承载能力连接起来了。

## 3\.2 核心业务应用

### 3\.2\.1 审批流转中枢（src/views/approval）

定位：全站审批业务的核心承载层。

职责：覆盖审批发起、待办、已办、抄送与审批详情等核心场景，围绕审批单生命周期组织页面交互。详情页统一承载表单渲染、节点权限、审批动作、评论附件、轨迹时间线、SLA 状态、代理关系、协同进度与 AI 建议展示，待办页则按当前处理人过滤任务，保证审批入口和处理视图一致。

这一层不是简单地把审批信息铺在页面上，而是承担“把表单、流程、权限、任务、轨迹、通知和辅助建议拼成一张完整业务视图”的职责，因此它是整个平台最能体现引擎化落地效果的地方。

### 3\.2\.2 表单与流程引擎中枢（src/components）

定位：审批配置化能力的基础引擎层。

职责：包含基于 form\-create 的动态表单渲染能力，以及基于 LogicFlow 的流程画布、节点配置和流程定义编辑能力。表单侧负责根据 Schema 完成字段渲染、只读禁用和运行时权限注入，流程侧负责节点、连线、事件与流程定义之间的双向映射，为审批模板配置和流程编排提供可视化支撑。

这一层的关键价值不在于“能渲染表单”或“能画流程图”，而在于把“可编辑模型”和“可执行模型”从页面层抽出来，沉淀为可持续复用的基础引擎。

### 3\.2\.3 文档与报表引擎（src/components/document \& src/workers）

定位：文档预览与报表处理的重交互能力层。

职责：内聚 Excel 导入导出、字段映射、预览校验、PDF 预览与 PDF 文本提取能力，并通过 Worker 拆分高开销任务，处理 ArrayBuffer 转换、表格解析、文本抽取和渲染等操作，提升大体量业务单据、附件预览与知识库接入场景下的稳定性。

对于审批系统来说，很多复杂度不只来自流程本身，也来自附件、报表和制度文档这类“长文本 / 大文件 / 重计算”对象。这一层把这些能力单独沉淀出来，避免它们散落在页面里。

### 3\.2\.4 高阶逻辑抽象层（src/composables）

定位：视图无关的组合式逻辑复用层。

职责：抽离审批域、表单域与辅助能力域的公共逻辑，包括 Schema 适配、审批详情派生、待办处理、列表筛选、节点权限控制、AI 建议状态机与异常处理等能力。通过组合式 API 将协议转换、状态计算和交互逻辑从页面中分离，提升业务复杂场景下的可维护性与复用度。

这一层是项目里控制复杂度的关键抓手。页面尽量只负责渲染和交互编排，复杂逻辑则尽量在 composables 中沉淀为可组合、可测试、可复用的单元，这也是前端平台型项目和普通页面型项目最明显的分界线之一。

### 3\.2\.5 契约中心与类型层（src/types）

定位：应用内部的数据契约与类型边界层。
职责：集中维护表单协议、流程定义、审批实体、任务状态和通知消息等核心 TypeScript 类型，并通过 `packages/contracts` 与 BFF 共享 AI 审批建议、SSE 事件、知识库与检索问答契约，保证表单 Schema、流程节点配置、审批任务流转以及页面状态之间的数据结构统一，降低跨模块协作中的理解和维护成本。
从架构价值上看，这一层的存在让前端页面不需要直接感知底层第三方结构、BFF 内部实现或 AI 原始响应，而是统一依赖内部稳定协议和共享契约。这种“协议隔离”本身就是平台能力的一部分。

### 3\.2\.6 BFF 后端服务层（apps/bff）

定位：审批业务的后端支撑层，承载审批协同、流程治理、AI 服务与审计追踪的核心逻辑。

职责如下：

- 审批域：支撑审批提交、处理动作（同意 / 驳回 / 转交 / 加签 / 催办 / 撤回 / 取消）、工作台统计、待办过滤、代理委托等能力。

- 流程治理域：支撑流程 CRUD、发布、回滚、版本查询、影响分析、规则调试等能力。

- AI 服务域：支撑审批上下文组装、提示词裁剪、结构化结果解析、流式输出与 `manual_review` 降级策略。

- 知识库域：支撑知识库创建、文档入库、文本分块、向量写入、检索召回、来源引用与 fallback 搜索等能力。

- 审计域：基于统一 AuditEvent 模型，在审批提交、审批处理、代理启停、流程发布、流程回滚等关键动作点自动写入审计日志，并提供列表查询、详情查看与导出能力。

- 实时推送：基于 SSE 推送审批状态变更、待办更新、AI 理由流式片段和消息通知到前端。
这一层最大的价值在于把“审批上下文治理、知识库调用、AI 辅助能力、审计追踪和数据存储”统一收口，避免这些高复杂度逻辑散落在前端页面或多个后端入口中。

## 3\.3 底层网络与质量基建

### 3\.3\.1 领域 API 与状态管理

项目通过 `src/api` 组织业务接口与 mock / real 双模式数据服务，以审批域为核心沉淀审批列表、详情、处理、通知、统计和代理配置等接口能力，并补充审计日志 API、AI 审批建议 API、知识库 CRUD 与检索 API。服务端状态由 TanStack Vue Query 负责缓存、失效刷新和请求联动，Pinia 承担用户信息、权限和全局状态管理，使审批列表、详情、工作台统计、消息提醒与知识库数据之间形成稳定的数据同步机制。
这种组织方式的好处是前端可以在保持 mock 开发效率的同时，平滑切换到 real 模式与 BFF 联调，不需要因为后端接入就推翻原有页面结构和状态组织方式。

### 3\.3\.2 公共工具与工程规范

项目在 `packages/utils` 中沉淀日期处理、格式化与通用工具能力，在 `packages/config` 中统一 ESLint、Prettier 与样式相关配置，在 `packages/contracts` 中维护前后端共享契约，在 `packages/ai-utils` 中抽象 AI 基础能力，保证项目在多人协作下具备一致的代码风格、稳定的共享边界和较低的维护摩擦。
这类公共层能力虽然不直接面向业务展示，但它们决定了项目在持续扩展时能否保持稳定、清晰和低耦合。

### 3\.3\.3 测试与验证体系

围绕审批主链路、引擎能力与智能增强场景，项目引入 Vitest 与 Playwright 构建测试体系。单元测试主要覆盖审批自动治理逻辑、任务迁移、会签或签策略、数据转换、AI 审批建议降级、知识库 CRUD 与 fallback 检索等能力。端到端测试则覆盖审批发起、待办处理、代理审批、升级流转等关键交互路径，用于保障审批域演进过程中的功能稳定性。

这里的重点不是“有测试”本身，而是测试覆盖的对象尽量靠近那些最容易出错、最影响业务口径一致性的引擎层能力。

## 3\.4 核心数据流转

### 3\.4\.1 审批主链路

1. 发起审批时，系统根据表单数据、流程定义和当前节点处理策略生成审批记录、节点任务与初始轨迹。

2. 待办列表以当前处理人为准过滤任务，确保代理接管、转交或升级后的待办归属能够及时反映到页面。

3. 审批详情页在加载审批数据后，结合节点上下文、字段权限和表单 Schema 动态生成可读写视图，并同步展示进度、轨迹、通知、协同状态和 AI 建议入口。

4. 审批处理阶段支持通过、驳回、转交、加签、催办、撤回与取消等动作，并根据当前节点的会签或签策略计算任务进度和流程结果。

5. 每次审批相关接口调用都会触发自动治理逻辑，对超时任务执行 SLA 自动升级，对存在有效规则的任务执行代理同步，保证责任归属与实际处理人状态一致。

6. 当用户手动触发 AI 建议时，前端仅传递 `approvalId`，由 BFF 内部读取审批详情、表单摘要、流程轨迹和制度上下文，返回 `suggestion / confidence / riskLevel / reasoning / disclaimer / generatedAt` 等结构化结果；若模型异常、信息不足或解析失败，则统一降级到 `manual_review`。

7. 列表、详情、统计、通知和操作轨迹通过统一的失效刷新机制保持联动，减少多页面切换时的数据滞后与状态不一致问题。
这条链路体现的是：审批系统的真正复杂度不只在“表单提交”，而在“节点流转、责任归属、协同处理、制度复核和状态一致性”这些环节能否被统一建模。

### 3\.4\.2 流表联动机制

项目以流程节点上下文作为主状态，以动态表单 Schema 作为客状态。当前端进入审批详情页后，会先解析当前节点权限，再对原始表单规则进行只读、禁用、隐显和操作态注入，使同一张单据能够在发起、审批、财务或协同节点下呈现不同的交互形态，实现单据视图随流程流转自动适配。

从设计角度看，这一机制让前端不需要为不同审批角色和节点分别维护独立页面，而是把视图差异收敛到统一协议 \+ 节点态权限之中，这正是平台化设计带来的直接收益。

### 3\.4\.3 审批自动治理能力

在审批域内部，任务模型区分了原责任人和当前处理人两层身份：原责任人用于表达任务归属，当前处理人用于决定待办展示和实际操作权限。基于这套任务模型，项目实现了代理审批与 SLA 自动升级两类自动治理能力，并将轨迹、通知、详情摘要和统计数据统一纳入同一套审批域状态流中，形成从发起到处理、再到协同和治理的完整闭环。

这一能力的核心价值在于，它不是单点功能，而是把多种复杂场景下最容易混乱的数据口径统一了，让状态一致性成为系统内建能力，而不是页面层补丁。

### 3\.4\.4 文档与报表协同链路

对于报销、财务和附件类审批场景，项目将表单、审批、文档处理与制度知识库能力打通。表单数据可进入 Excel 映射与导出链路，附件与制度类 PDF 可复用同一套预览与文本抽取能力，审批详情页则在需要时挂接制度依据检索与来源引用展示。

这条链路的重点不在于“上传了文件”，而在于前端把单据、附件、制度文档这三类对象通过统一处理路径组织起来，使审批平台具备更强的资料承载能力和复核支撑能力。

### 3\.4\.5 流程版本治理与审计闭环

在流程治理侧，项目采用全快照式版本策略管理流程定义。每次创建、更新、发布、回滚都会生成完整快照，配合版本号、状态、操作人、备注和时间线信息，支撑流程历史可回看、可比较、可回退。发布前提供影响分析，回滚时提供风险提示与二次确认，保证流程治理过程具备可解释性。

与此同时，关键治理动作和关键审批动作统一接入 AuditEvent 模型，记录操作人、动作类型、模块、结果、before / after 快照、TraceId、IP、UA、耗时与关联链接，形成从治理动作到追溯证据的完整闭环。这一层把“平台配置能力”进一步升级成了“治理能力”。

# 4 项目亮点

## 4\.1 动态表单适配层

项目最值得讲的第一个亮点，不是“用了 form\-create”，而是我在其之上补了一层内部表单协议和适配器，把设计器规则、业务表单结构和运行时渲染格式隔离开了。这样业务页面不直接依赖第三方规则结构，字段属性、校验规则、组件映射和权限注入都收口在适配层完成。

这个亮点的价值在于协议稳定。后续无论换表单引擎、补字段类型、加联动规则，主要改的是适配层和渲染层，而不是全量修改业务页面，所以它体现的是平台抽象能力，而不是组件使用能力。

## 4\.2 流程编排与领域模型双向映射

第二个亮点是把流程画布的编辑模型和审批执行的领域模型拆开了。LogicFlow 负责交互和画布体验，真正用于保存和执行的则是内部的 WorkflowDefinition；两者通过 `graph -> definition` 和 `definition -> graph` 的双向映射连接起来。
这个设计的价值在于把“能编辑”和“能执行”分层。画布结构不会直接绑死审批协议，审批领域模型也不会被图库内部结构污染，因此流程定义既能稳定回显，也能稳定执行，适合继续扩展复杂审批规则。

## 4\.3 审批自动治理与闭环一致性

第三个亮点是审批闭环不是只做到“能提交、能处理”，而是补上了任务模型、代理审批、SLA 自动升级、会签或签策略、轨迹、通知和统计一致性。项目把 owner 和 handler 拆开，用任务模型解释责任归属和实际处理人，再通过统一治理入口驱动列表、详情、统计和通知同步更新。

这个亮点最容易打动面试官的地方在于，它直接回答了复杂审批系统最容易混乱的问题：为什么待办归属、详情权限、轨迹记录和统计口径能对得上。这里讲的是状态一致性能力，而不是单个功能点。

## 4\.4 流程治理、审计追溯与 AI 边界控制

第四个亮点是把流程平台能力进一步做到了治理层。流程定义不是一次性配置，而是带版本、带发布、带回滚、带影响分析的治理对象；关键动作都统一进入审计模型，能解释是谁在什么时间做了什么调整，并且可以追溯到前后变化。
在这套治理链路上，AI 的接入被明确限制为辅助层：它只能读取审批上下文、制度依据和轨迹信息，返回结构化建议，并在异常时降级到 `manual_review`。也就是说，系统同时具备“更智能”和“可追责”两种属性，而不是为了智能牺牲责任边界。

## 4\.5 一分钟总结版

如果让我用一分钟总结这个项目，我会说：这不是一个“加了 AI 的审批页面集合”，而是一个以前端为主导的审批平台原型。我先把动态表单、流程定义、节点权限、任务模型和审批闭环抽象成统一平台能力，再在这套主链路上接入 AI 审批建议和制度知识库，让系统既能承载复杂中后台协同场景，也能体现智能增强能力，但 AI 始终只是辅助层，不直接驱动真实审批动作。

## 4\.6 面试时的表达建议

讲这 4 点时，顺序最好固定成“先讲平台抽象，再讲复杂业务闭环，最后补充 AI 增强与边界控制”。不要一上来就堆名词，也不要把 Ark、Qdrant、RAG 这类词放在最前面。面试官更想听的是，你为什么要把审批系统做成协议驱动的引擎化平台，这样设计解决了什么复杂度问题。
如果面试官偏业务视角，就多讲审批闭环、一致性、制度复核和风险控制；如果面试官偏技术视角，就多讲协议适配、领域模型、共享契约、自动治理和运行时权限注入。AI 相关内容最后补充即可，重点讲“怎么接入审批上下文、用于什么场景、输出为什么要结构化、为什么必须 `manual_review`”。

# 5 高频面试

## 5\.1 第一维度：动态表单与协议适配

### 5\.1\.1 Q1：为什么选 form\-create，而不是自己手写一套 JSON 表单解析器？

回答：我更看重的是成熟的渲染、校验和规则承载能力，而不是单纯把组件映射出来。自己写一套简单解析器不难，但一旦涉及字段校验、联动规则、只读禁用、运行时权限注入和后续扩展，维护成本会迅速失控；用 form\-create 可以把精力集中在内部表单协议、适配层和平台化规则承载上。

- 追问：那你在这个项目里真正自己做了什么？

- 补充回答：我没有把 form\-create 直接暴露给业务页面，而是在 `useFormSchemaAdapter` 和 `DynamicForm` 之间补了一层协议转换和权限变异。这一层负责协议隔离、组件映射、规则标准化和节点态权限注入，这部分才是项目里的核心实现。

### 5\.1\.2 Q2：如果设计器规则、后端数据结构和运行时表单格式不一致，你怎么处理？

回答：我用的是适配器模式。先把设计器规则统一转换成内部的 `FormFieldSchema`，再把 required、pattern、range、min / max 这类校验规则标准化，最后由渲染层消费统一协议。这样第三方规则结构、后端数据结构和前端运行时格式就被适配层隔离开了。

- 追问：这样做最大的价值是什么？

- 补充回答：最大的价值是协议稳定。以后换表单引擎、补字段类型、加校验规则，主要改适配层和渲染层，不需要全量改业务页面。对平台型项目来说，协议隔离比库本身更重要。

### 5\.1\.3 Q3：如果某个审批节点要把一半字段变只读，另一半字段隐藏，你怎么做？

回答：我不会去改原始 Schema，而是在运行时做节点态注入。动态表单先拿基础规则，再结合当前节点权限做一次规则变异；如果页面是只读态，还会统一给字段补 `disabled / readonly`，这样同一份表单协议就可以适配不同审批节点。

- 追问：这样会不会污染原始规则？

- 补充回答：不会，运行时处理的是派生后的规则结构，不是直接回写原始协议，所以可以做到对原始 Schema 零侵入。这也是“运行时权限注入”而不是“配置写死”的关键区别。

## 5\.2 第二维度：流程编排与流表联动

### 5\.2\.1 Q4：为什么选 LogicFlow，而不是直接自己维护节点数组，或者用别的图库？

回答：因为这个项目需要的不只是“能画图”，还要支持拖拽、节点编辑、连线事件、只读预览和流程定义回填。LogicFlow 在流程编排场景里更贴业务，输出也是相对容易处理的 JSON 结构，和 Vue 组件集成成本也可控。

- 追问：你在这个项目里最看重它哪一点？

- 补充回答：我最看重的是它和业务定义之间比较容易做双向映射。也就是画布交互模型和审批执行模型可以拆开，前者负责“可编辑”，后者负责“可执行”，不会把审批协议绑死在图库结构上。

### 5\.2\.2 Q5：流程图数据怎么保证“能编辑、能保存、还能稳定回显”？

回答：我把 `WorkflowDefinition` 作为业务领域模型，把 LogicFlow 图数据作为编辑模型，分别做了 `definition -> graph` 和 `graph -> definition` 两个方向的转换。这样保存时存的是业务定义，编辑时用的是图形结构，回显时再做一次映射，画布只是交互壳子。

- 追问：为什么不直接把 LogicFlow 原始数据存起来？

- 补充回答：因为原始图数据更偏渲染和交互，不适合直接作为审批执行协议。审批真正关心的是节点类型、处理人、条件、权限和超时配置，这些应该沉淀在业务定义层，而不是图库结构里。

### 5\.2\.3 Q6：表单和流程是怎么打通的？同一张单据为什么能在不同节点呈现不同形态？

回答：流程节点是主状态，表单 Schema 是客状态。进入详情页后，我会先解析当前节点、任务进度和节点权限，再把这些信息传给动态表单层，让它决定字段的读写、隐显和按钮态；所以同一张单据在发起、审批、财务这些节点下，看到的是不同的交互视图。

- 追问：这和普通的 RBAC 权限有什么区别？

- 补充回答：这里不是菜单权限，而是节点上下文驱动的字段权限。真正决定页面能不能操作的，不只是用户角色，还有当前流程走到哪个节点、当前处理人是谁，所以它是运行时映射，不是角色写死。

## 5\.3 第三维度：审批闭环与自动治理

### 5\.3\.1 Q7：你们的会签和或签是怎么实现的？

回答：我在审批任务里保留了当前节点任务集合和节点模式。`or` 模式下，一个人通过就自动关闭其他待处理任务；`and` 模式下，所有人都通过节点才结束，同时驳回逻辑也按模式分别处理，所以进度、状态、通知和轨迹都是跟着节点策略一起算的。

- 追问：为什么这块不能只看审批单状态？

- 补充回答：因为审批单状态是结果，真正决定流程怎么走的是当前节点任务集合和处理进度。如果没有任务层，协同审批、加签、自动关闭剩余任务这些场景都很难准确表达，所以这里的核心是任务模型。

### 5\.3\.2 Q8：代理审批和 SLA 自动升级分别是什么？为什么要拆开做？

回答：代理审批是“人不在时，别人代我处理”，SLA 自动升级是“超过时效没人处理，系统自动改派”。我在任务模型里拆了 owner 和 handler 两层身份，owner 表示责任归属，handler 表示当前实际处理人，这样代理、升级、待办归属和详情权限才能统一解释。

- 追问：如果升级和代理同时存在，顺序怎么定？

- 补充回答：我这里定的是先升级、再代理。也就是先确定任务升级后归谁，再判断新的责任人有没有代理规则，这样责任归属和实际处理人都能解释得通，状态口径也更稳定。

### 5\.3\.3 Q9：审批后为什么待办、详情、统计、通知能保持一致？

回答：我把审批相关自动治理统一收口在审批域 API 层，每次查列表、查详情、处理审批、查统计、查通知时都会先跑自动治理，再通过 Vue Query 的 `invalidateQueries` 触发列表、详情、统计和通知的失效刷新。这样所有页面走的是同一套数据源，而不是各自维护一份状态。

- 追问：这里最大的收益是什么？

- 补充回答：最大的收益是状态一致性。用户处理完审批后，不需要手动刷新多个页面，待办归属、详情轨迹、工作台统计和通知提醒会一起更新，不容易出现页面之间数据打架。

### 5\.3\.4 Q10：你觉得这个项目最值得讲的技术价值是什么？

回答：不是单独某个库选得多漂亮，而是我把动态表单、流程编排、审批治理和 AI 辅助串成了一条完整链路。前端既承担了协议适配，也承担了节点态渲染、任务状态承载、审批闭环治理和 AI 交互承载，所以这个项目能讲的不只是页面开发，而是一个前端主导的平台型审批项目。

- 追问：如果面试官继续深挖，你最建议往哪两个点展开？

- 补充回答：我会优先展开两个点。第一是动态表单适配层，讲协议隔离和运行时权限注入；第二是审批闭环，讲会签或签、代理审批、SLA 自动升级以及状态一致性。AI 可以作为第三个补充亮点，但不建议一开始就把它当主叙事。

## 5\.4 第四维度：流程治理、审计追溯与 AI 边界（新增）

### 5\.4\.1 Q11：流程版本治理和审计链路你是怎么一起设计的？

回答：我采用了全快照式版本策略，每次创建、更新、发布、回滚都生成完整快照。版本列表展示版本号、操作人、时间、状态、备注，发布前提供影响分析，回滚时支持版本可选 \+ 风险提示 \+ 二次确认。同时我把这些关键动作统一接入 AuditEvent 模型，写入操作人、动作、模块、结果、before / after 快照、TraceId、IP、UA、耗时和关联链接，形成从治理动作到追溯证据的完整链路。

- 追问：为什么用全快照而不是增量 diff？

- 补充回答：全快照保证了回滚的原子性和可验证性，实现简单，适合 MVP 阶段。增量 diff 在当前 demo 项目里复杂度更高，且对演示价值和交付效率的收益不明显。

### 5\.4\.2 Q12：AI 审批建议为什么只做辅助，不直接驱动审批动作？

回答：因为审批系统的核心风险在于责任归属和决策可追溯，AI 可以帮助提升判断效率，但不能替代真实审批人。我这里采用的是 Human\-in\-the\-Loop 设计：前端只传 `approvalId`，BFF 内部读取审批上下文并裁剪敏感信息，统一返回 `suggestion`、`confidence`、`riskLevel`、`reasoning`、`disclaimer`、`generatedAt` 等结构化结果；如果模型缺失、解析失败或信息不足，就统一降级到 `manual_review`。

- 追问：这样设计最大的价值是什么？

- 补充回答：最大的价值是把“智能能力”和“真实动作”明确分层。AI 可以提升效率，但不会绕过节点权限、角色边界和审计链路，系统因此仍然保持可控、可解释和可回退。

- 追问：那知识库和 AI 审批建议是什么关系？

- 补充回答：我把知识库理解成制度依据层，把 AI 建议理解成辅助判断层。知识库负责提供制度条款、文档片段和引用来源，AI 建议则在审批上下文、轨迹信息和制度依据基础上生成结构化辅助意见。两者配合之后，系统更像“带依据的辅助审查”，而不是“黑盒自动审批”。

# 6 表单类型、角色与权限设计

## 6\.1 表单类型划分

在该审批项目中，前端接入的核心审批表单主要分为三类。第一类是假勤类单据，如请假、出差、加班，这类单据通常涉及时间区间、请假类型、证明材料和销假补录等字段，联动规则较多；第二类是费用类单据，如报销、借款、付款申请，这类单据通常包含金额、明细、附件、预算校验和财务核验字段，流程链路较长；第三类是采购与行政类单据，如采购申请、合同审批、用印申请等，这类单据更强调节点流转、附件查看和跨部门协作。
从当前代码实现来看，审批主链路已稳定承载 `leave`、`expense`、`purchase` 三类表单，并且能够在审批详情页根据单据类型自动解析对应表单协议和流程定义。也就是说，前端不是为每一类单据单独维护一套页面，而是把表单类型抽象成“表单 Schema \+ 流程定义 \+ 节点权限”的协议组合，再由运行时动态渲染。
在这个基础上，AI 建议和制度知识库并不是额外平行的一套页面逻辑，而是附着在同一套审批详情上下文之上，为不同类型单据提供辅助判断与制度依据补充。

## 6\.2 角色语义与前端实现边界

从业务语义上看，审批参与方通常包括发起人、直属主管、部门负责人、财务、HR、行政以及流程管理员等。这些角色决定了流程在组织层面的责任分工，比如谁发起、谁审核、谁复核、谁归档。但在前端实现里，真正决定页面展示和交互权限的，并不只是“用户属于哪个角色”，而是“当前流程走到哪个节点、当前任务实际归谁处理”。

同一个用户在不同流程、不同节点下，能够看到的字段、能够执行的操作、是否拥有处理权限，都可能完全不同。因此前端并没有为“主管页面”“财务页面”“HR 页面”分别维护独立视图，而是以“当前节点 \+ 当前任务处理人 \+ 节点权限配置”作为运行时判断依据。这也是这个项目里比较关键的一点：角色信息负责描述组织语义，节点上下文负责驱动页面渲染。前端真正消费的是节点权限、任务状态和处理人身份，而不是把角色直接硬编码进页面组件。

AI 建议与制度知识库则位于辅助层，只为当前处理人提供参考，不参与角色判定本身，也不具备越过节点权限边界的能力。

## 6\.3 权限模型设计

这个项目的权限设计不是停留在菜单权限和数据权限，而是进一步下沉到了节点权限和字段权限四个层次。

1. 菜单权限：决定用户能否进入审批相关模块，例如待办、已办、抄送、代理设置等页面。

2. 数据权限：决定用户能查看哪些审批单据，例如“我发起的”“待我处理的”“抄送给我的”。

3. 节点权限：决定当前用户在当前节点是否可以执行审批、转交、加签、催办、撤回、取消等动作。

4. 字段权限：决定当前节点下某个字段是 `editable`、`readonly`、`hidden` 还是 `required`。
从代码结构看，动态表单本身同时支持两类控制来源。一类是字段自身的联动规则，例如 `requiredWhen`、`visibleWhen`、`disabledWhen`，用于解决字段之间的条件依赖；另一类是节点权限映射 `PermissionsMap`，用于解决流程上下文驱动的只读、隐藏和必填要求。也就是说，字段联动回答的是“表单内部条件成立时字段怎么变”，节点权限回答的是“流程走到当前节点时字段应该怎么变”。
这种拆分很重要，因为它让前端不必为每个节点维护一份独立表单，而是在运行时基于同一份原始 Schema 叠加节点态权限，实现同单据、多节点、多视图的自适应呈现。AI 建议不属于权限模型的一部分，它只能读取审批上下文并返回辅助结论，不能绕过节点权限直接触发审批动作。

## 6\.4 当前项目中的权限落地方式

在审批详情页，前端会先根据审批记录解析出当前单据对应的表单协议，再解析当前节点、当前节点任务和节点权限，然后把这些信息一起交给动态表单组件。动态表单内部先基于 Schema 生成基础规则，再结合节点权限做一次权限变异，如果当前页是只读态，还会统一给字段补上 `disabled` 或 `readonly` 属性。
这意味着权限不是写死在页面模板里，而是通过“基础表单协议 \+ 节点权限映射 \+ 运行时状态”三者组合得到最终渲染结果。前端页面只关心当前节点和当前处理人，不关心这张单据是不是来自 HR、财务还是主管页面，因为这些差异都已经被折叠进节点权限模型里了。
另外，在审批待办场景里，列表过滤也不是按申请人或组织角色，而是按当前任务处理人过滤。这样在代理审批、转交审批、SLA 自动升级这些场景下，待办归属才会和详情权限保持一致，不会出现“列表里有待办，但详情页不能处理”或者“详情页显示可处理，但待办不归我”的状态错位问题。AI 建议卡片则挂在详情页辅助区域，只在已有审批上下文和权限判定完成后提供参考，不参与真实权限计算。

## 6\.5 典型案例一：报销单

报销单是一个典型的跨节点联动场景，也是最能体现“同一张单据，不同节点表现不同”的类型。在发起节点，用户通常需要填写报销事由、报销金额、费用明细、发生日期、附件等基础信息，这一阶段以录入和校验为主，大部分字段处于可编辑状态。当流程流转到直属主管节点后，表单的核心目标已经不是继续填单，而是让主管进行合理性审核。因此前端会把大部分申请字段切换为只读，只保留审批意见、审批动作和必要的上下文信息。这样主管看到的是“审核视图”，而不是“填单视图”。
进入财务节点后，单据又会进入另一种语义环境。此时前端可能需要额外展示发票核验、预算校验、付款方式、财务备注等字段；其中部分字段会动态显示，部分字段会变为必填，而申请人原始填写的信息则继续保持只读。整个过程中，前端始终渲染的是同一份报销单 Schema，但由于当前节点变化，字段的展示状态、编辑权限和校验要求随之变化，这正是跨节点联动的典型体现。
如果面试官追问这套能力前端是怎么做到的，你可以直接回答：我没有为主管审批页、财务审批页分别写独立页面，而是通过节点权限映射控制字段在运行时切换为 `editable / readonly / hidden / required`，让同一张单据在不同审批节点下生成不同视图。进一步叠加 AI 建议后，系统也只是基于当前单据摘要、附件信息和轨迹给出风险提示，不会改变字段权限和审批动作边界。

## 6\.6 典型案例二：请假单

请假单同时体现了“跨字段联动”和“跨节点联动”两类能力，所以非常适合作为面试里的例子。发起阶段，员工需要填写请假类型、请假时间、请假天数、请假原因和证明材料等信息。这一阶段的重点不是节点权限，而是字段之间的业务依赖关系。例如当请假类型选择“病假”时，证明材料字段需要自动显示并变为必填；如果选择其他类型，这个字段则可以隐藏或降级为非必填。这个变化不是由流程节点触发的，而是由表单内部字段值触发的，属于跨字段联动。

随后当流程进入主管审批节点后，前端会把申请人原始填写的信息整体切换为只读，只保留审批意见和审批动作等入口。进入 HR 节点后，又可能额外出现 HR 审核意见、假期余额确认、销假补录等字段，同时部分历史字段继续保持只读。这一阶段的变化已经不再是字段之间的依赖，而是当前流程节点对表单展示和权限的重新定义，因此属于跨节点联动。

如果面试官继续追问“这两类联动有什么本质区别”，你可以这样回答：跨字段联动解决的是表单内部条件依赖，比如 A 字段的值影响 B 字段的显示和校验；跨节点联动解决的是流程上下文变化，比如同一张表单在发起、主管审批、HR 审核阶段呈现不同的字段权限和操作态。制度知识库的价值则是在病假证明、请假制度解释等场景下提供制度条款引用，辅助人工复核，而不是替代节点判断。

## 6\.7 设计总结

这一类审批系统真正难的，不是表单字段多，也不是流程节点多，而是如何在不复制页面的前提下，让同一张单据随着流程状态变化自动切换视图。这个项目的核心设计思路是：表单负责承载业务字段，流程负责承载节点上下文，权限模型负责把两者在运行时连接起来。角色是业务语义，节点是渲染依据，字段权限是最终落点；AI 建议和制度知识库位于辅助层，只为当前处理人提供解释、风险提示和制度依据，不改变真实审批边界。

所以从前端视角看，这套系统并不是“给不同角色分别写页面”，而是基于统一的表单协议，在运行时结合当前节点、当前处理人、字段联动和节点权限动态生成审批视图。这样既降低了维护成本，也让审批单据在类型扩展、流程变更、规则调整和 AI 能力叠加时更容易持续演进。
