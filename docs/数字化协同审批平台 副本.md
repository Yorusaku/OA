# 数字化协同审批平台
## 项目定位
该项目是一个面向中大型企业审批场景的前端主导型智能协同审批平台原型，核心目标不是继续为不同单据和不同角色堆叠页面，而是把审批系统从“页面硬编码”演进为“协议驱动 + 引擎渲染 + 状态可追踪”的平台化交付模式。
项目聚焦审批规则频繁变化、流程协同复杂、单据处理低效、制度复核依赖人工经验、AI 辅助能力边界难以解释等场景，围绕“动态表单 + 流程引擎 + 审批治理”的主线建设，并在此基础上接入 AI 审批建议、制度知识库、Prompt 模板管理和 AI 决策审计，形成可演进、可追踪、可解释的智能增强层。
从项目定位上看，它不是若干审批页面的集合，也不是以 AI 为主语的自动化审批系统，而是把审批领域里真正具备复用价值的能力沉淀出来，包括表单协议层、流程定义层、节点权限层、审批任务模型、自动治理机制、流程版本治理、审计追踪，以及附着在审批上下文之上的 AI 辅助判断链路。
当前项目是简历和 Demo 场景下的原型，重点体现平台化设计、前端工程化和 AI 应用接入思路，不将其表述为已经承载真实生产流量的完整企业产品。
最终形成的是“审批执行主链路 + 制度复核支撑 + AI 辅助建议 + AI 治理闭环”的体系，既能体现复杂中后台平台能力，也能体现智能增强能力，但 AI 始终停留在 Human-in-the-Loop 的辅助层，不越过真实审批边界。

## 一分钟总结
如果让我用一分钟总结这个项目，我会说：这不是一个“加了 AI 的审批页面集合”，而是一个以前端为主导的智能审批平台原型。我先把动态表单、流程定义、节点权限、任务模型和审批闭环抽象成统一平台能力，再在这套主链路上接入 AI 审批建议、制度知识库和 AI 治理体系，让系统既能承载复杂中后台协同场景，也能体现智能增强能力，但 AI 始终只是辅助层，不直接驱动真实审批动作。
## 三分钟讲述思路
1. 先讲平台抽象：为什么不为每类审批单独写页面，而是做动态表单、流程定义、节点权限和任务模型。
1. 再讲审批闭环：为什么要处理会签或签、代理审批、SLA 升级、转交、加签、催办、撤回、取消和状态一致性。
1. 然后讲流程治理：为什么流程版本要支持发布、回滚、影响分析和审计追踪。
1. 再讲 AI 增强：AI 如何读取审批上下文、知识库和轨迹信息，并输出结构化建议。
1. 最后讲 AI 边界：Policy-as-Code、AI 审计、Prompt 模板、推理溯源和不确定性标注如何保证 AI 可控、可解释、可追踪。

# 系统架构设计
## 宏观架构策略
### 架构定位
考虑到中大型企业审批规则频繁变化、单据类型持续扩展、流程协同链路复杂以及小团队维护成本有限，项目在业务交付层面采用前端主导 + BFF 支撑的模块化单体架构。
前端不再只是消费接口和渲染页面的薄壳，而是承担表单协议适配、节点态渲染、审批视图编排、流程画布交互、任务状态承载和 AI 交互展示等职责；BFF 则作为审批上下文治理、数据存储协调、服务端规则收口、AI 服务接入和审计追踪的支撑层。
### 引擎化建设思路
传统 OA 审批系统的问题通常不是页面不够多，而是表单、流程、权限、状态、通知和审计被拆散在不同页面和接口里。一旦流程、字段或角色发生变化，就需要多处同步修改。
项目将前端实现重点从页面开发转向引擎能力建设，业务侧主要通过表单 Schema、流程定义和节点配置驱动界面渲染与审批流转，前端负责协议解析、状态适配和交互承载，BFF 负责审批上下文组装、结构化服务与存储支撑。
### 重计算前置策略
针对财务报表导入导出、电子单据预览、PDF 文本提取等重交互场景，项目将部分高频重计算能力前置到前端，结合 Web Worker 承担 Excel 解析、数据映射、PDF 文本抽取与预览等任务，减少主线程阻塞。
这一策略也服务于知识库链路：制度类 PDF 在前端先完成文本提取，再以 JSON 文本形式发送到 BFF，尽量复用审批附件预览和制度知识库的文档处理路径。当前原型采用 JSON 文本上传，并不宣称支持 Word 原生直传。

## 核心业务应用
### 审批流转中枢
审批流转中枢覆盖审批发起、待办、已办、抄送和审批详情等核心场景，围绕审批单生命周期组织页面交互。
详情页统一承载表单渲染、节点权限、审批动作、评论附件、轨迹时间线、SLA 状态、代理关系、协同进度和 AI 建议展示；待办页则按当前处理人过滤任务，保证审批入口和处理视图一致。
这一层不是简单地把审批信息铺在页面上，而是把表单、流程、权限、任务、轨迹、通知和辅助建议拼成一张完整业务视图。
### 表单与流程引擎中枢
表单侧基于 form-create 根据 Schema 完成字段渲染、只读禁用和运行时权限注入；流程侧基于 LogicFlow 完成节点、连线、事件与流程定义之间的双向映射。
关键价值不在于“能渲染表单”或“能画流程图”，而在于把可编辑模型和可执行模型从页面层抽出来，沉淀为可持续复用的基础引擎。
### 文档与报表引擎
文档与报表引擎内聚 Excel 导入导出、字段映射、预览校验、PDF 预览和 PDF 文本提取能力，并通过 Worker 拆分高开销任务。
对于审批系统来说，复杂度不只来自流程，也来自附件、报表和制度文档等长文本、大文件和重计算对象。单独沉淀这些能力，可以避免它们散落在业务页面里。
### 高阶逻辑抽象层
| Composable 或模块 | 主要职责 |
|---|---|
| `useFormSchemaAdapter` | Designer 规则到内部表单协议的转换 |
| `useApprovalDetail` | 派生表单、节点、任务、权限、轨迹和时间线 |
| `useNodePermissions` | 管理节点字段权限和运行时同步 |
| `useApprovalSubmit` | 统一审批动作校验和提交 |
| `useAiSuggestion` | 管理 AI 建议生成、流式状态、中断和重试 |
| `useAiPolicy` | 查询策略并展示策略警告 |
| `useAiAudit` | 查询统计并回写采纳或覆盖反馈 |
| `usePromptTemplate` | 管理 Prompt 模板列表、详情、CRUD 和测试 |
页面尽量只负责渲染和交互编排，复杂逻辑在 Composable 中沉淀为可组合、可测试、可复用的单元。
### 契约中心与类型层
项目通过 `packages/contracts` 与 BFF 共享审批、AI、SSE、RAG、审计和 Prompt 模板契约，保证表单 Schema、流程节点配置、审批任务流转以及页面状态之间的数据结构统一。
契约层让前端页面不需要直接感知底层第三方结构、BFF 内部实现或 AI 原始响应，而是统一依赖内部稳定协议和共享类型。
# 核心数据流转
## 审批主链路
1. 发起审批时，系统根据表单数据、流程定义和当前节点处理策略生成审批记录、节点任务与初始轨迹。
1. 待办列表以当前处理人为准过滤任务，确保代理接管、转交或升级后的待办归属能够及时反映到页面。
1. 审批详情页加载审批数据后，结合节点上下文、字段权限和表单 Schema 动态生成可读写视图，并展示进度、轨迹、通知、协同状态和 AI 建议入口。
1. 审批处理阶段支持通过、驳回、转交、加签、催办、撤回与取消，并根据当前节点的会签或签策略计算任务进度和流程结果。
1. 审批相关接口触发自动治理逻辑，对超时任务执行 SLA 自动升级，对存在有效规则的任务执行代理同步，保证责任归属与实际处理人状态一致。
1. 用户手动触发 AI 建议时，前端仅传递 `approvalId`，由 BFF 读取审批详情、表单摘要、流程轨迹和制度上下文，返回结构化建议；模型异常、信息不足或解析失败时降级到 `manual_review`。
1. 列表、详情、统计、通知和操作轨迹通过 Query 失效刷新及实时事件保持联动，减少多页面切换时的数据滞后与状态不一致。
## 流表联动机制
项目以流程节点上下文作为主状态，以动态表单 Schema 作为客状态。当前端进入审批详情页后，会先解析当前节点、当前节点任务和节点权限，再把这些信息传给动态表单层，让它决定字段读写、隐显、必填和按钮态。
```text
流程节点上下文
-> 当前节点、任务状态、处理人、节点模式
-> 节点权限映射
-> 表单 Schema 运行时变异
-> editable / readonly / hidden / required
-> 动态表单渲染和审批操作态
```
发起节点可能需要录入字段，主管节点可能大多只读，财务节点可能新增核验字段，HR 节点可能需要假期余额确认。前端不需要为每个节点写独立页面，而是基于同一份 Schema 做运行时权限注入。
## 审批自动治理能力
| 能力 | 处理对象 | 设计重点 |
|---|---|---|
| 代理审批 | owner 与 delegate | 在有效时间范围内将当前处理人切换为代理人 |
| 转交审批 | 当前任务 | 改变当前处理人，并保留操作轨迹 |
| SLA 升级 | 超时任务 | 将超时任务升级给预设处理人并记录升级状态 |
| 会签 | 同一节点多个任务 | 所有任务完成后再推进，或按规则处理拒绝 |
| 或签 | 同一节点多个任务 | 任一有效处理人完成后推进节点 |
| 催办 | 当前待办 | 记录催办动作并通知当前处理人 |
| 责任拆分 | owner / handler | 保留原责任人，同时表达当前实际处理人 |
审批任务模型区分 `owner` 和 `handler`：`owner` 表示原责任人，`handler` 表示当前实际处理人。代理审批、转交审批和 SLA 自动升级会影响 `handler`，但不一定改变 `owner`。
这种拆分可以解释谁本来应该处理、谁现在实际处理、待办列表应该归谁、详情页谁能操作以及轨迹里应该记录什么。
## 流程版本治理与审计闭环
流程治理侧采用全快照式版本策略。每次创建、更新、发布或回滚都会生成完整快照，配合版本号、状态、操作人、备注和时间线信息，支撑流程历史回看、版本比较和回退。
关键治理动作和关键审批动作统一接入 `AuditEvent` 模型，记录操作人、动作类型、模块、结果、before / after 快照、TraceId、IP、User-Agent、耗时与关联链接，形成从治理动作到追溯证据的闭环。
## AI 建议链路
```text
前端点击生成建议
-> 前端只传 approvalId
-> BFF 读取审批详情、表单摘要、流程轨迹、SLA、代理信息和知识库上下文
-> Policy-as-Code 策略校验
-> block 命中则直接返回 manual_review，不调用 LLM
-> warn 命中则继续调用 LLM，但降低置信度并附加警告
-> Prompt 模板渲染
-> Ark LLM 生成结构化结果
-> Zod 校验并解析 reasoningSegments 和 uncertainties
-> BFF 补齐 reviewSummary、riskPoints 和 evidenceItems
-> SSE 流式推送到前端
-> 前端展示审批 Copilot 审查卡、溯源片段和不确定性提示
-> 人工采纳或覆盖后回写 AI 审计
```
# AI 增强与治理体系
## AI 审批建议
AI 审批建议的输入边界比较克制：前端不传完整表单和敏感上下文，只传 `approvalId`。BFF 内部读取审批详情、表单摘要、流程轨迹、SLA 状态、代理关系、最近意见、附件摘要和制度上下文，再统一组装 Prompt。
输出统一为结构化结果，包括 `suggestion`、`confidence`、`riskLevel`、`reasoning`、`reasoningSegments`、`uncertainties`、`reviewSummary`、`riskPoints`、`evidenceItems`、`disclaimer`、`generatedAt` 和可选的 `auditEventId`。
| 输出字段 | 作用 |
|---|---|
| `suggestion` | `approve`、`reject` 或 `manual_review` |
| `confidence` | 表示模型建议的置信度，用于人工复核分流 |
| `riskLevel` | 表示低、中、高风险等级 |
| `reasoning` | 展示模型综合判断理由 |
| `reviewSummary` | 展示审批标题、申请人、类型、金额、节点和时间线 |
| `riskPoints` | 展示规则或模型识别出的风险点 |
| `evidenceItems` | 展示制度、表单、历史和模型判断依据 |
| `reasoningSegments` | 将理由拆分为可追溯的来源片段 |
| `uncertainties` | 提醒审批人需要重点核对的不确定信息 |
| `disclaimer` | 明确 AI 仅供参考，最终以人工审批为准 |
### 审批 Copilot 审查卡
审批 Copilot 审查卡不是重新做一个通用聊天助手，而是把原来的 AI 建议卡片升级成可复核的审批审查视图。
审查卡聚合四类信息：
- 审批摘要：包括标题、申请人、类型、金额、当前节点和关键时间线。
- 风险点：由 BFF 根据高金额、SLA 升级、多次催办、描述缺失、附件缺失等规则确定性生成，也可以合并模型风险判断。
- 依据来源：优先从 `reasoningSegments` 映射出知识库、表单数据、历史数据和模型判断来源。
- 模型建议：展示建议结果、置信度、理由和不确定性。
这个设计的重点是混合生成：基础事实和规则风险由 BFF 确定性生成，避免模型把金额、节点、附件等事实编错；AI 负责综合判断、理由表达和溯源解释。
模型不可用时仍然降级为 `manual_review`，但审查摘要、规则风险和兜底依据仍然可以展示，用户不会只看到一个失败提示。
## Human-in-the-Loop 边界
| 边界 | 具体要求 |
|---|---|
| 审批动作 | AI 只提供建议，不直接触发 `approve / reject / transfer / addSign / remind / withdraw / cancel` |
| 权限判断 | AI 不参与节点权限、字段权限和角色判断 |
| 当前处理人 | AI 不能绕过当前处理人边界 |
| 最终决策 | 最终审批结果由人工确认和提交 |
| 异常场景 | 信息不足、模型缺失、解析失败、策略阻断或高风险场景倾向 `manual_review` |
## Policy-as-Code
Policy-as-Code 用声明式规则定义 AI 能力边界，规则包含作用域、优先级、条件、效果和提示信息。当前策略可以覆盖超时升级、高金额、代理审批、多次催办和缺少描述等风险场景。
| 策略效果 | 行为 | 是否调用 LLM |
|---|---|---|
| `allow` | 正常生成建议并保留免责声明 | 是 |
| `warn` | 允许生成建议，降低置信度并展示警告 | 是 |
| `block` | 直接返回 fallback，要求人工复核 | 否 |
最重要的设计点是：AI 边界先于模型调用执行，而不是等模型给出结果后再补一句免责声明。
## 决策审计四维度
AI 审计不只是记录“调用了一次模型”，而是围绕建议生命周期做全链路留痕。
| 审计维度 | 记录内容 |
|---|---|
| 输入上下文 | 审批 ID、审批类型、金额、风险信号、知识库命中数、Prompt 模板版本 |
| 模型行为 | 建议结果、置信度、风险等级、理由、模型名、Token 用量、延迟 |
| 人工干预 | 是否采纳、是否覆盖、覆盖原因、实际决策、操作人和时间 |
| 结果影响 | 最终审批结果、建议是否匹配、策略是否阻断、策略警告列表 |
## 采纳与覆盖反馈闭环
AI 建议展示后，审批人可以采纳建议，也可以覆盖建议。采纳和覆盖都不是前端本地状态，而是回写 BFF 审计服务，形成 AI 建议生成、人工采纳或人工覆盖的生命周期链路。
这套闭环可以统计采纳率、覆盖率、风险分布和平均延迟，也能用于后续分析哪些场景适合 AI 辅助、哪些场景需要加强规则或知识库建设。
## Prompt 模板管理
Prompt 模板不直接硬编码在业务页面里，而是通过模板服务做 CRUD、版本化、激活和在线测试。同一作用域下只有一个 active 模板，其他模板可以处于 draft 或 archived 状态。
模板支持 `{{var}}` 变量替换和 `\{\{#cond\}\}...\{\{/cond\}\}` 条件块渲染，用于将审批上下文、策略警告、流程摘要、轨迹摘要和表单摘要注入 Prompt。
模板有默认 fallback，避免模板缺失时 AI 建议链路整体不可用。生产环境还需要进一步补充模板权限、审批发布和敏感变量治理。
## 可解释性溯源
AI 理由会被拆成多个 `reasoningSegments`，每个片段包含内容、来源、置信度和可选引用信息。
| 来源类型 | 代表含义 |
|---|---|
| `knowledge_base` | 来自制度知识库或文档片段 |
| `form_data` | 来自当前审批单的表单字段 |
| `historical_data` | 来自历史审批记录、流程轨迹或统计上下文 |
| `model_judgment` | 模型基于上下文形成的综合判断 |
这样前端展示的不再只是“一段理由”，而是可以让审批人看到某个判断来自制度、当前表单、历史信息还是模型综合判断。
## 不确定性标注
不确定性标注只用于提示人工重点核对，不直接改变建议本身，也不能绕过审批权限。
典型场景包括：
- 表单描述不完整；
- 附件缺失或无法识别；
- 制度依据存在多个版本；
- 关键金额、时间或人员信息需要人工确认；
- 模型无法从当前上下文得到充分结论。
## 知识库与 RAG
知识库更准确地说是审批场景下的制度知识库检索与依据展示，不把它夸成通用 RAG 平台。
```text
TXT / Markdown / PDF 文档
-> 前端提取文本或读取文本内容
-> BFF 保存文档元数据和原文
-> 文本分块
-> Embedding 向量化
-> 写入 Qdrant
-> 根据审批类型和上下文检索相关片段
-> 将制度依据注入 Prompt 或展示在审查卡
```
首版支持 TXT、Markdown 和 PDF。PDF 文本提取放在前端 Worker 中，减少主线程阻塞；向量链路失败时允许文档元数据落库并保留 fallback，不阻塞基础文档管理。
知识库对话可以支持多会话、流式输出、中断、重试、重命名、删除、Markdown 渲染和来源引用，但它只提供制度检索与解释，不直接驱动审批动作。
## AI 审计看板
AI 审计看板围绕建议生命周期提供统计和日志查询能力。
| 看板指标 | 说明 |
|---|---|
| 采纳率 | AI 建议被人工采纳的比例 |
| 覆盖率 | AI 建议被人工修改或覆盖的比例 |
| 置信度分布 | 不同置信度区间的建议数量 |
| 风险分布 | 低、中、高风险建议的分布 |
| 平均延迟 | 从生成请求到完成的平均耗时 |
| 策略命中 | `allow`、`warn`、`block` 的命中情况 |

## 动态表单适配层
| 维度 | 说明 |
|---|---|
| 背景 | 单据类型和字段规则变化频繁，页面硬编码维护成本高 |
| 方案 | 使用 Adapter 将 Designer 规则转换成内部 FormSchema |
| 实现 | 统一字段类型、组件属性、默认值和校验规则，再由动态表单渲染 |
| 价值 | 新增单据类型主要通过协议和配置扩展，减少业务页面重复开发 |
## 流程编排与领域模型双向映射
| 维度 | 说明 |
|---|---|
| 编辑模型 | LogicFlow 负责节点、连线、拖拽和画布交互 |
| 业务模型 | 流程定义负责节点类型、处理人、条件、权限和超时配置 |
| 转换方向 | `definition -> graph` 用于回显，`graph -> definition` 用于保存 |
| 价值 | 画布负责可编辑，领域模型负责可执行，避免把审批协议绑定到图库 |
## 审批自动治理与闭环一致性
| 难点 | 解决方式 |
|---|---|
| 代理导致待办归属变化 | 用 `owner` 保留原责任人，用 `handler` 表示实际处理人 |
| 转交改变当前处理人 | 后端统一更新任务、轨迹、通知和列表归属 |
| SLA 超时升级 | 在服务端识别超时任务并执行升级，同时记录升级轨迹 |
| 会签或签状态复杂 | 根据节点模式和任务完成情况统一计算节点进度 |
| 多页面状态滞后 | 使用 Query 失效刷新和实时事件同步列表、详情和通知 |
## 流程治理与审计追溯
流程版本采用全快照方式，每次发布、回滚和关键更新都有完整版本记录。
审计日志使用统一的 `AuditEvent` 模型记录操作人、动作、结果、before / after、TraceId、耗时和关联链接，既可以用于问题排查，也可以支持流程变更追溯。
## AI 增强与治理闭环
AI 能力不是单独挂在审批页面上的黑盒按钮，而是嵌入审批上下文和人工决策流程。
```text
审批上下文
-> Policy 边界判断
-> Prompt 模板渲染
-> 结构化 AI 建议
-> SSE 流式展示
-> 风险点和依据来源解释
-> 人工采纳或覆盖
-> AI 审计和统计
```
这个设计把 AI 建议、规则风险、制度依据和人工反馈放在同一张 Copilot 审查卡里，让输出从一段建议文本变成可解释、可治理、可复核的辅助审查对象。
## 前端平台化价值
项目的核心价值不是做了多少页面，而是把审批系统中可复用的能力抽象成平台层：
- 表单协议解决单据变化；
- 流程定义解决流程变化；
- 节点权限解决运行时视图变化；
- 任务模型解决审批状态变化；
- 版本和审计解决配置变化的可追溯性；
- AI 治理解决智能能力接入后的边界和解释问题。
# 表单类型、角色与权限设计
## 表单类型划分
| 表单类型 | 典型单据 | 主要特点 |
|---|---|---|
| 假勤类 | 请假、出差、加班 | 时间区间、证明材料和字段联动较多 |
| 费用类 | 报销、借款、付款申请 | 金额、明细、附件、预算和财务核验较重要 |
| 采购与行政类 | 采购申请、合同审批、用印申请 | 流程节点、附件查看和跨部门协作较重要 |
## 角色语义与前端实现边界
| 概念 | 含义 | 前端关注点 |
|---|---|---|
| 申请人 | 发起审批的人 | 控制发起、撤回和查看自己的申请 |
| 节点处理人 | 当前审批节点实际需要处理的人 | 控制待办和审批操作入口 |
| 原责任人 | 任务最初归属的人 | 在代理或升级后仍保留责任关系 |
| 代理人 | 在有效代理时间内代替责任人处理任务的人 | 反映当前任务处理权变化 |
| 抄送人 | 只接收过程或结果信息的人 | 可以查看，但不能执行审批动作 |
| 管理员 | 管理流程、模板、策略和审计的人 | 访问系统管理能力，不等于拥有所有审批权限 |
角色是业务语义，节点是运行时上下文，字段权限是最终渲染落点。前端可以展示和辅助判断，但真正的权限校验必须由服务端收口。
## 权限模型设计
| 权限层级 | 作用 | 典型判断 |
|---|---|---|
| 菜单权限 | 决定是否可以进入模块 | 待办、已办、代理设置、AI 审计和 Prompt 管理 |
| 数据权限 | 决定可以查看哪些单据 | 我发起的、待我处理的、抄送给我的 |
| 节点权限 | 决定当前节点能执行哪些动作 | 审批、转交、加签、催办、撤回、取消 |
| 字段权限 | 决定字段在当前节点的状态 | `editable`、`readonly`、`hidden`、`required` |
动态表单同时支持两类控制来源：
- 字段自身的联动规则，例如 `requiredWhen`、`visibleWhen`、`disabledWhen`，用于解决字段之间的条件依赖；
- 节点权限映射，用于解决流程上下文驱动的只读、隐藏和必填要求。
字段联动回答“表单内部条件成立时字段怎么变”，节点权限回答“流程走到当前节点时字段应该怎么变”。
## 当前项目中的权限落地方式
审批详情页会先根据审批记录解析表单协议，再解析当前节点、当前节点任务和节点权限，然后把这些信息一起交给动态表单组件。
动态表单内部先基于 Schema 生成基础规则，再结合节点权限做一次权限变异；如果当前页是只读态，还会统一给字段补上 `disabled` 或 `readonly` 属性。
权限最终由“基础表单协议 + 节点权限映射 + 运行时状态”三者组合得到，而不是写死在页面模板里。
待办列表按当前任务处理人过滤，而不是简单按申请人或组织角色过滤。这样在代理审批、转交审批和 SLA 自动升级场景下，待办归属才会和详情权限保持一致。
## 典型案例：报销单
报销单是典型的跨节点联动场景，也最能体现“同一张单据，不同节点表现不同”。
| 审批节点 | 主要交互 | 字段状态 |
|---|---|---|
| 发起节点 | 填写事由、金额、明细、日期和附件 | 大部分字段可编辑并参与校验 |
| 直属主管 | 审核合理性并填写审批意见 | 申请字段大多只读，保留审批入口 |
| 财务节点 | 发票核验、预算校验、付款方式和财务备注 | 部分字段动态显示或变为必填 |
整个过程中前端始终渲染同一份报销单 Schema，只是根据当前节点改变字段展示状态、编辑权限和校验要求。
## 典型案例：请假单
请假单同时体现跨字段联动和跨节点联动。
发起阶段，员工填写请假类型、请假时间、请假天数、请假原因和证明材料。当请假类型选择“病假”时，证明材料字段可以自动显示并变为必填；选择其他类型时，该字段可以隐藏或降级为非必填。
进入主管审批节点后，申请人填写的信息整体切换为只读，只保留审批意见和审批动作。进入 HR 节点后，又可以展示 HR 审核意见、假期余额确认或销假补录等字段。
跨字段联动解决“字段 A 的值影响字段 B 的显示和校验”，跨节点联动解决“流程上下文变化后同一张表单的权限和操作态变化”。
## 权限设计总结
审批系统真正难的不是字段多或节点多，而是在不复制页面的前提下，让同一张单据随着流程状态变化自动切换视图。
项目的核心设计是：表单负责承载业务字段，流程负责承载节点上下文，权限模型负责把两者在运行时连接起来。AI 建议和制度知识库位于辅助层，只提供解释、风险提示和制度依据，不改变真实审批边界。
# 高频面试 QA
## 动态表单与协议适配
### 为什么选 form-create，而不是自己手写 JSON 表单解析器？
**回答**：我更看重成熟的渲染、校验和规则承载能力，而不是单纯把组件映射出来。自己写简单解析器不难，但一旦涉及字段校验、联动规则、只读禁用、运行时权限注入和后续扩展，维护成本会快速上升。使用 form-create 后，我可以把精力集中在内部表单协议、适配层和平台规则承载上。
**具体实现**：项目没有把 form-create 直接暴露给业务页面，而是在 `useFormSchemaAdapter` 和动态表单组件之间增加协议转换和权限变异层，负责协议隔离、组件映射、规则标准化和节点态权限注入。
**可能追问**：第三方库未来替换怎么办？
**补充回答**：主要改 Adapter 和渲染层，业务页面依赖的是内部 `FormSchema`，因此可以降低替换成本。
### 设计器规则、后端数据结构和运行时格式不一致怎么办？
**回答**：使用适配器模式。先把设计器规则转换成内部表单协议，再把 `required`、`pattern`、`range`、`min / max` 等校验规则标准化，最后由渲染层消费统一协议。
**价值**：第三方规则结构、后端数据结构和前端运行时格式被隔离，后续换引擎、补字段类型或增加校验规则，主要修改适配层和渲染层。
### 一个节点把部分字段设为只读、另一部分隐藏，怎么做？
**回答**：不直接修改原始 Schema，而是在运行时生成派生规则。动态表单先拿基础规则，再结合当前节点权限做规则变异；只读态统一补充 `disabled / readonly` 属性。
**关键点**：运行时处理的是派生结构，不回写原始协议，因此可以做到对原始 Schema 零侵入。
## 流程编排与流表联动
### 为什么选 LogicFlow，而不是自己维护节点数组？
**回答**：项目需要的不只是画图，还要支持拖拽、节点编辑、连线事件、只读预览和流程定义回填。LogicFlow 能提供画布交互，同时输出相对容易处理的结构化数据，和 Vue 集成成本可控。
**关键取舍**：画布模型负责“可编辑”，审批领域模型负责“可执行”，两者通过转换层连接，不把审批协议绑定在图库结构上。
### 流程图数据如何保证能编辑、保存和稳定回显？
**回答**：把流程定义作为业务领域模型，把 LogicFlow 图数据作为编辑模型，分别实现 `definition -> graph` 和 `graph -> definition` 两个方向的转换。保存时存业务定义，编辑时使用图形结构，回显时再做映射。
**为什么不直接存图数据**：图数据偏渲染和交互，审批真正关心的是节点类型、处理人、条件、权限和超时配置，这些应该沉淀在业务定义层。
### 表单和流程怎么打通？
**回答**：流程节点是主状态，表单 Schema 是客状态。进入详情页后先解析当前节点、任务进度和节点权限，再把这些信息传给动态表单层，决定字段读写、隐显和按钮态。
**和普通 RBAC 的区别**：菜单和角色权限决定能否进入模块，而节点和字段权限决定当前这张单据在当前流程节点下如何呈现。
## 审批闭环与自动治理
### 会签和或签怎么实现？
**回答**：会签和或签本质上是同一审批节点下多个任务的完成策略。会签要求多个任务按照节点规则完成后再推进；或签允许任一有效处理人完成后推进。系统通过节点模式、任务状态和进度数据统一计算节点是否完成。
**实现重点**：任务记录具体处理人和状态，节点实例记录当前节点和进度，BFF 在审批动作后统一重新计算，而不是由前端直接决定流程结果。
### 代理审批和 SLA 自动升级有什么区别？
**回答**：代理审批是预先配置的时间范围和责任委托，解决某个责任人暂时无法处理的问题；SLA 自动升级是任务超时后的系统治理动作，解决长时间无人处理的问题。两者都会影响当前处理人，但触发条件和业务含义不同。
**设计重点**：保留 `owner` 和 `handler` 两层身份，既能表示原始责任关系，也能表示当前实际处理人。
### 审批后如何保证待办、详情、统计和通知一致？
**回答**：审批动作由 BFF 统一收口，在同一个业务处理过程中更新审批记录、任务、轨迹、通知和相关统计；前端提交成功后通过 Query 失效刷新，并结合实时事件更新列表和详情。
**生产化补充**：真实生产环境还需要事务、幂等键、消息可靠投递和分布式一致性方案，当前 Demo 主要体现模块边界和刷新机制。
### 项目最值得讲的技术价值是什么？
**回答**：不是做了多少审批页面，而是把审批领域中可复用的能力抽象成了平台层。动态表单解决单据变化，流程引擎解决流程变化，任务模型和自动治理解决复杂流转，版本和审计解决配置追溯，AI 治理解决智能能力的边界和解释问题。
## 流程治理、审计与 AI 边界
### 流程版本治理和审计如何设计？
**回答**：流程采用全快照版本策略，创建、更新、发布和回滚都生成完整快照，并记录版本号、状态、操作人、备注和时间线。关键流程治理动作和审批动作统一写入审计事件，记录 before / after、TraceId、结果和关联对象。
**价值**：既能回看历史配置，也能定位某次流程变化对审批行为的影响。
### AI 为什么只做辅助，不直接驱动审批？
**回答**：审批涉及权限、责任和风险，AI 输出存在不确定性，不能绕过当前处理人和节点权限。因此 AI 只输出建议、风险点、依据和不确定性，真实审批动作仍然由具备权限的人工触发。
**边界**：AI 不参与角色判断、字段权限判断和审批动作授权。
### AI 的能力边界怎么控制？
**回答**：通过 Policy-as-Code 在模型调用前执行声明式策略判断。`block` 直接返回 `manual_review` 并且不调用模型；`warn` 允许调用但降低置信度并展示警告；`allow` 正常生成，同时保留免责声明。
### AI 决策如何追溯？
**回答**：围绕建议生命周期记录四类审计信息：输入上下文、模型行为、人工干预和结果影响。生成时记录审批摘要、风险信号、知识库命中数、模型结果和耗时；采纳或覆盖时记录操作人、实际决策和覆盖原因。
### Prompt 为什么不能直接写死在代码里？
**回答**：写死会导致模板迭代需要发版，也不利于版本回滚、在线测试和不同业务作用域管理。项目通过 Prompt 模板服务提供 CRUD、版本化、激活和变量渲染，并保留默认 fallback，避免模板缺失影响主链路。
### AI 建议凭什么可信？
**回答**：不把可信度建立在模型一句话上，而是采用结构化输出、规则风险、依据来源、置信度和不确定性共同呈现。基础事实和规则风险由 BFF 确定性生成，模型负责综合判断；审批人仍然可以查看依据并进行人工复核。
### 知识库和 AI 审批建议是什么关系？
**回答**：知识库是制度依据层，AI 建议是综合判断层。系统根据审批类型、金额、附件和流程上下文检索相关制度片段，再把依据注入模型上下文或展示在审查卡里，让审批人能核对建议背后的制度来源。
### AI 审计看板有什么价值？
**回答**：它把 AI 调用从一次性功能变成可度量的业务闭环，可以观察采纳率、覆盖率、置信度分布、风险分布、平均延迟和策略命中情况，为后续优化 Prompt、规则和知识库提供依据。
## AI 应用落地追问
### 项目里的 AI 到底怎么用？
**回答**：主要用于审批详情页的辅助审查。系统根据审批单、流程轨迹、节点任务、SLA、附件和制度知识库上下文，生成结构化的审批建议、风险点、依据来源和不确定性提示，帮助审批人更快完成复核，但不直接替代审批动作。
### 前端对接了哪些 AI 相关接口？
**回答**：前端主要消费审批建议查询或流式生成接口、策略查询接口、AI 审计统计和反馈接口、Prompt 模板管理接口，以及知识库管理、检索和对话流式接口。
**前端工作重点**：使用 Composable 管理请求状态、SSE 事件、打字机效果、中断、重试、错误提示、来源展示和人工反馈。
### 为什么前端只传审批单 ID？
**回答**：如果前端把完整表单和上下文直接传给模型，容易造成数据边界混乱，也不利于权限控制和审计。只传 `approvalId` 可以让 BFF 统一完成上下文聚合、字段裁剪、权限校验和策略判断，保证不同入口得到一致的审查口径。
### AI 返回为什么要结构化？
**回答**：审批人需要快速看到建议、风险、依据和需要核对的内容，不能只依赖一段自由文本。因此返回对象包含建议结果、置信度、风险等级、审查摘要、风险点、依据来源、推理溯源、不确定性和审计标识，便于前端稳定渲染、BFF 审计和后续统计。
### SSE 为什么选择 POST 加 fetch，而不是 EventSource？
**回答**：EventSource 原生只支持 GET，而生成 AI 建议时需要在请求体中传递 `approvalId`、策略选项等参数，因此采用 POST 加 fetch 的 `ReadableStream` 读取方式。前端通过 `AbortController` 支持中断，并根据 `meta`、`chunk`、`segment`、`uncertainty`、`done` 和 `error` 事件更新状态。
### 知识库是不是完整的 RAG 平台？
**回答**：不会把它夸成通用 RAG 平台。它更准确地说是审批场景下的制度知识库检索与依据展示，目标是让审批建议有制度来源可追溯，而不是做万能问答机器人。
### 如果面试官问具体使用什么大模型 API？
**回答**：可以说明项目通过 AI 服务层对接 Ark 等模型能力，但前端不直接绑定具体模型厂商。我的重点是把审批上下文、知识库依据、流式输出、结构化结果、异常降级和人工反馈闭环打通，后续可以通过统一模型服务或 AI 网关替换底层模型。

## 流程执行引擎补充

审批动作不是在页面里把状态直接改成完成，而是由 BFF 根据流程定义的边推进实例：发起时从 start 节点解析首个审批节点；审批节点完成后继续遍历边，条件节点使用表单数据命中分支，CC 节点只生成抄送记录并继续流转，到达 end 或无下一审批节点时才结束。会签和或签仍然是当前节点的任务完成策略，因此多节点流程中的每个节点都可以独立配置。

详情页将流程 definition 和实例状态映射为只读运行态流程图，明确标识已完成、当前、待达和驳回节点；历史定义不可用时回退到审批轨迹时间线，避免图形展示影响主链路可用性。批量审批采用 BFF 单次端点逐条隔离处理并返回逐项结果，发起页草稿则通过独立 CRUD 支持保存、回填和删除。

### 为什么不让前端决定下一节点？

**回答**：下一节点取决于流程定义、表单数据、当前节点策略和待办归属，属于服务端领域规则。由 BFF 统一推进，才能让单条审批、批量审批、通知、轨迹和审计采用同一口径；前端只负责展示运行态和刷新查询结果。

### Docker 化后如何验证服务不是“容器能启动就算完成”？

**回答**：Compose 让 BFF 等待 PostgreSQL healthcheck，通过容器服务名连接 PostgreSQL 与 Qdrant，再使用 BFF 的 `/health` 检查实际 HTTP 可用性。镜像采用 Node 20 ESM，内部相对导入显式使用 `.js` 后缀，避免开发环境解析宽松、容器运行时找不到模块的问题。
