# 1 数字化协同审批平台
## 1.1 项目定位
该项目是一个面向中大型企业审批场景的前端主导型智能协同审批平台原型，核心目标不是继续为不同单据和不同角色堆叠页面，而是把审批系统从“页面硬编码”演进为“协议驱动 + 引擎渲染 + 状态可追踪”的平台化交付模式。
项目聚焦审批规则频繁变化、流程协同复杂、单据处理低效、制度复核依赖人工经验、AI 辅助能力边界难以解释等场景，围绕“动态表单 + 流程引擎 + 审批治理”的主线建设，并在此基础上接入 AI 审批建议、制度知识库、Prompt 模板管理和 AI 决策审计，形成可演进、可追踪、可解释的智能增强层。
从项目定位上看，它不是若干审批页面的集合，也不是以 AI 为主语的自动化审批系统，而是把审批领域里真正具备复用价值的能力沉淀出来，包括表单协议层、流程定义层、节点权限层、审批任务模型、自动治理机制、流程版本治理、审计追踪，以及附着在审批上下文之上的 AI 辅助判断链路。
最终形成的是“审批执行主链路 + 制度复核支撑 + AI 辅助建议 + AI 治理闭环”的完整体系，既能体现复杂中后台平台能力，也能体现智能增强能力，但 AI 始终停留在 Human-in-the-Loop 的辅助层，不越过真实审批边界。
## 1.2 项目技术栈
Vue 3.5 + TypeScript 5.9 + Vite 7 + pnpm 10 + Turborepo 2 + Pinia + TanStack Vue Query + form-create 3.2 + LogicFlow 2.1 + Tailwind CSS 4 + Element Plus + Fastify 5.6 + PostgreSQL 16 + Qdrant + 火山方舟 Ark + Zod 4 + Vitest 4 + Playwright 1.58
## 1.3 项目职责
- 动态表单：负责引入 form-create 搭建 JSON 驱动表单渲染与校验链路，替代按单据类型硬编码页面的开发方式，提升复杂审批单据接入效率与后续规则变更的可维护性。
- 协议适配：负责封装表单 Schema 适配层，完成设计器规则到内部表单协议的转换，统一字段属性、组件映射、校验逻辑与渲染入口，隔离第三方规则结构对业务页面的直接影响。
- 流程编排：参与审批流程可视化重构，基于 LogicFlow 完成节点、连线、事件与流程定义之间的映射和编辑能力建设，支撑流程配置的可视化、可回填与可执行。
- 流表联动：结合审批节点上下文、任务状态与字段权限，动态控制表单读写、隐显、必填和操作状态，实现审批详情视图的自适应渲染。
- 审批闭环：参与审批域核心链路建设，完善发起、审批、转交、加签、催办、撤回与取消等能力，打通待办、详情、通知、统计与轨迹联动。
- 自动治理：参与代理审批、SLA 自动升级、任务责任归属与当前处理人拆分等机制设计，保证转交、代理、超时升级等复杂场景下列表、详情、通知和统计口径一致。
- 流程治理：主导流程版本治理与审计闭环建设，实现发布、回滚、影响分析、版本历史可视化，并将关键操作统一接入审计日志模型。
- 规范沉淀：沉淀表单协议、流程节点配置、共享契约与组合式能力边界，统一审批场景接入方式，降低后续维护、扩展与联调成本。
- AI 增强：参与审批详情页 AI 建议卡片接入，设计 Human-in-the-Loop 置信度分流、流式理由输出与 manual_review 降级策略，确保 AI 只做辅助判断，不越过真实审批边界。
- 知识库建设：参与制度知识库链路落地，打通 TXT / Markdown / PDF 文档上传、前端文本提取、分块、检索问答与引用来源展示，支撑审批场景下的制度复核。
## 1.4 一分钟总结
如果让我用一分钟总结这个项目，我会说：这不是一个“加了 AI 的审批页面集合”，而是一个以前端为主导的智能审批平台原型。我先把动态表单、流程定义、节点权限、任务模型和审批闭环抽象成统一平台能力，再在这套主链路上接入 AI 审批建议、制度知识库和 AI 治理体系，让系统既能承载复杂中后台协同场景，也能体现智能增强能力，但 AI 始终只是辅助层，不直接驱动真实审批动作。
## 1.5 三分钟讲述思路
1. 第一层先讲平台抽象：为什么不为每类审批写页面，而是做动态表单、流程定义、节点权限和任务模型。
2. 第二层讲审批闭环：为什么要处理会签或签、代理审批、SLA 升级、转交、加签、催办、撤回、取消和状态一致性。
3. 第三层讲治理能力：为什么流程版本要支持发布、回滚、影响分析和审计追踪。
4. 第四层讲 AI 增强：AI 如何读取审批上下文、知识库和轨迹信息，输出结构化建议。
5. 第五层讲 AI 边界：Policy-as-Code、AI 审计、Prompt 模板、推理溯源和不确定性标注如何保证 AI 可控、可解释、可追踪。
# 2 技术选型与工程基础
## 2.1 工程与质量基建
- 构建与开发环境：采用 Vite 7 + pnpm 10 + Turborepo 2 的 Monorepo 架构，保障高频业务迭代效率，同时让 web、bff、contracts、ai-utils 等模块能够在统一仓库中协同演进。
- 开发语言：TypeScript 5.9，严格执行静态类型规范，确保表单 Schema、流程定义、审批任务模型、AI 结构化结果与知识库契约在前后端之间具备稳定一致的数据边界。
- 质量保障：引入 Vitest 搭建单元测试防线，并通过 Playwright 补齐关键交互路径验证；测试重点覆盖表单适配、审批治理、会签或签策略、流程版本治理、审计日志、AI 降级与知识库检索等核心链路。
## 2.2 应用核心架构
- 前端框架：Vue 3.5 + Composition API，采用 `<script setup>` 与组合式模式，将审批详情派生、节点权限控制、任务状态计算、AI 建议状态机等复杂逻辑进行解耦与复用。
- 服务端状态：使用 TanStack Vue Query 接管后端 API 请求，利用缓存、请求去重、失效刷新和多页面联动能力维护审批列表、详情、通知、知识库和 AI 审计状态。
- 客户端状态：Pinia 集中管理用户信息、菜单权限、筛选条件、当前视图状态与审批域共享状态，保证业务交互的一致性与可维护性。
- 路由管理：Vue Router 承载审批中心、流程设计、知识库、系统日志、AI 审计看板和 Prompt 模板管理等模块化页面。
- 组合式基建：复杂业务逻辑尽量下沉到 composables，页面尽量保持轻薄，重点 composable 包括 `useApprovalDetail`、`useNodePermissions`、`useAiSuggestion`、`useAiPolicy`、`useAiAudit`、`usePromptTemplate`。
## 2.3 核心业务引擎
- 动态表单引擎：form-create 基于 JSON 规则驱动动态表单生成，结合 Element Plus 落地复杂字段联动、校验、只读禁用与运行时权限注入。
- 流程编排引擎：LogicFlow 负责审批流程图的可视化编排、节点配置、连线校验与流程定义编辑，支撑画布交互模型与审批领域模型之间的双向映射。
- 文档处理引擎：xlsx + pdfjs-dist + comlink + Web Worker 承担 Excel 导入导出、字段映射、PDF 预览与 PDF 文本提取等重计算任务。
- AI 与检索基础能力：`@oa/ai-utils` + 火山方舟 Ark + Qdrant 封装 LLM 调用、Embedding、文本分块、向量写入与检索能力，但它的定位是审批平台的增强型基础设施，不是主链路骨架。
## 2.4 数据与服务支撑
- BFF：Fastify 5.6 承载审批服务、流程治理、AI 建议、知识库、审计日志、Prompt 模板和 SSE 推送。
- 数据库：PostgreSQL 16 用于审批主数据、流程定义、版本快照、审计日志、知识库元数据和文档原文。
- 向量检索：Qdrant 用于制度文档分块后的向量存储和相似度检索。
- 契约校验：Zod 用于 BFF schema 校验，避免 AI 原始响应和 API 入参直接污染业务层。
# 3 系统架构设计
## 3.1 宏观架构策略
### 3.1.1 架构定位
考虑到中大型企业审批规则频繁变化、单据类型持续扩展、流程协同链路复杂以及小团队维护成本有限，项目在业务交付层面采用前端主导 + BFF 支撑的模块化单体架构。核心目标不是为每类审批单独开发页面，而是围绕动态表单、可视化流程编排、审批闭环治理和节点权限控制，构建一套可持续复用、可持续演进的平台型审批原型。
前端不再只是消费接口、渲染页面的薄壳，而是承担表单协议适配、节点态渲染、审批视图编排、流程画布交互、任务状态承载和 AI 交互展示等职责；BFF 则作为审批上下文治理、数据存储协调、服务端规则收口、AI 服务接入与审计追踪的后端支撑层。
### 3.1.2 引擎化建设思路
传统 OA 审批系统的问题通常不是“页面不够多”，而是表单、流程、权限、状态、通知和审计被拆散在不同页面和接口里，后续一旦流程变更、字段变更或角色变更，就需要多处同步修改。
这个项目的思路是把前端实现重点从页面开发转向引擎能力建设。业务侧主要通过表单 Schema、流程定义和节点配置驱动界面渲染与审批流转，前端负责协议解析、状态适配和交互承载，BFF 负责审批上下文组装、结构化服务与存储支撑，从而降低复杂审批单据的接入与变更成本。
### 3.1.3 重计算前置策略
针对财务报表导入导出、电子单据预览、PDF 文本提取等重交互场景，项目将部分高频重计算能力前置到前端，结合 Web Worker 承担 Excel 解析、数据映射、PDF 文本抽取与预览等任务，减少主线程阻塞，提升弱网和大体量数据场景下的可用性与响应速度。
这一策略也服务于知识库链路：制度类 PDF 在前端先完成文本提取，再以 JSON 文本形式发送到 BFF，既减少后端接入复杂度，也让文档处理路径在审批附件预览和制度知识库场景中尽量复用。

## 3.3 核心业务应用
### 3.3.1 审批流转中枢
审批流转中枢覆盖审批发起、待办、已办、抄送与审批详情等核心场景，围绕审批单生命周期组织页面交互。详情页统一承载表单渲染、节点权限、审批动作、评论附件、轨迹时间线、SLA 状态、代理关系、协同进度与 AI 建议展示，待办页则按当前处理人过滤任务，保证审批入口和处理视图一致。
这一层不是简单地把审批信息铺在页面上，而是承担“把表单、流程、权限、任务、轨迹、通知和辅助建议拼成一张完整业务视图”的职责，因此它是整个平台最能体现引擎化落地效果的地方。
### 3.3.2 表单与流程引擎中枢
表单侧基于 form-create 根据 Schema 完成字段渲染、只读禁用和运行时权限注入；流程侧基于 LogicFlow 完成节点、连线、事件与流程定义之间的双向映射，为审批模板配置和流程编排提供可视化支撑。
这一层的关键价值不在于“能渲染表单”或“能画流程图”，而在于把“可编辑模型”和“可执行模型”从页面层抽出来，沉淀为可持续复用的基础引擎。
### 3.3.3 文档与报表引擎
文档与报表引擎内聚 Excel 导入导出、字段映射、预览校验、PDF 预览与 PDF 文本提取能力，并通过 Worker 拆分高开销任务，处理 ArrayBuffer 转换、表格解析、文本抽取和渲染等操作，提升大体量业务单据、附件预览与知识库接入场景下的稳定性。
对于审批系统来说，很多复杂度不只来自流程本身，也来自附件、报表和制度文档这类长文本、大文件、重计算对象。这一层把这些能力单独沉淀出来，避免它们散落在页面里。
### 3.3.4 高阶逻辑抽象层
高阶逻辑抽象层通过 composables 抽离审批域、表单域与辅助能力域的公共逻辑，包括 Schema 适配、审批详情派生、待办处理、列表筛选、节点权限控制、AI 建议状态机、AI 策略警告、AI 审计回写和 Prompt 模板管理等能力。
页面尽量只负责渲染和交互编排，复杂逻辑则尽量在 composables 中沉淀为可组合、可测试、可复用的单元，这也是前端平台型项目和普通页面型项目最明显的分界线之一。
### 3.3.5 契约中心与类型层
项目通过 `packages/contracts` 与 BFF 共享审批、AI、SSE、RAG、审计和 Prompt 模板契约，保证表单 Schema、流程节点配置、审批任务流转以及页面状态之间的数据结构统一，降低跨模块协作中的理解和维护成本。
从架构价值上看，这一层让前端页面不需要直接感知底层第三方结构、BFF 内部实现或 AI 原始响应，而是统一依赖内部稳定协议和共享契约。这种“协议隔离”本身就是平台能力的一部分。
# 4 核心数据流转
## 4.1 审批主链路
1. 发起审批时，系统根据表单数据、流程定义和当前节点处理策略生成审批记录、节点任务与初始轨迹。
2. 待办列表以当前处理人为准过滤任务，确保代理接管、转交或升级后的待办归属能够及时反映到页面。
3. 审批详情页在加载审批数据后，结合节点上下文、字段权限和表单 Schema 动态生成可读写视图，并同步展示进度、轨迹、通知、协同状态和 AI 建议入口。
4. 审批处理阶段支持通过、驳回、转交、加签、催办、撤回与取消等动作，并根据当前节点的会签或签策略计算任务进度和流程结果。
5. 每次审批相关接口调用都会触发自动治理逻辑，对超时任务执行 SLA 自动升级，对存在有效规则的任务执行代理同步，保证责任归属与实际处理人状态一致。
6. 当用户手动触发 AI 建议时，前端仅传递 `approvalId`，由 BFF 内部读取审批详情、表单摘要、流程轨迹和制度上下文，返回结构化建议；若模型异常、信息不足或解析失败，则统一降级到 `manual_review`。
7. 列表、详情、统计、通知和操作轨迹通过统一的失效刷新机制保持联动，减少多页面切换时的数据滞后与状态不一致问题。
## 4.2 流表联动机制
项目以流程节点上下文作为主状态，以动态表单 Schema 作为客状态。当前端进入审批详情页后，会先解析当前节点、当前节点任务和节点权限，再把这些信息传给动态表单层，让它决定字段读写、隐显、必填和按钮态。
这套机制解决的是“同一张单据在不同节点呈现不同形态”的问题。发起节点可能需要录入字段，主管节点可能大多只读，财务节点可能新增核验字段，HR 节点可能需要假期余额确认。前端不需要为每个节点写独立页面，而是基于同一份 Schema 做运行时权限注入。
## 4.3 审批自动治理能力
审批任务模型区分了 owner 和 handler 两层身份：owner 表示原责任人，handler 表示当前实际处理人。代理审批、转交审批和 SLA 自动升级都会影响 handler，但并不一定改变 owner。
这种拆分让系统可以解释复杂场景：谁本来应该处理、谁现在实际处理、待办列表应该归谁、详情页谁能操作、轨迹里应该记录什么。它保证了待办、详情、通知和统计口径一致。
## 4.4 流程版本治理与审计闭环
流程治理侧采用全快照式版本策略管理流程定义。每次创建、更新、发布、回滚都会生成完整快照，配合版本号、状态、操作人、备注和时间线信息，支撑流程历史可回看、可比较、可回退。
关键治理动作和关键审批动作统一接入 AuditEvent 模型，记录操作人、动作类型、模块、结果、before / after 快照、TraceId、IP、UA、耗时与关联链接，形成从治理动作到追溯证据的完整闭环。
## 4.5 AI 建议链路
```text
前端点击生成建议
-> 只传 approvalId
-> BFF 读取审批详情、表单摘要、流程轨迹、SLA、代理信息和知识库上下文
-> Policy-as-Code 策略校验
-> block 命中则直接 manual_review，不调用 LLM
-> warn 命中则继续调用 LLM，但降低置信度并附加警告
-> Prompt 模板渲染
-> Ark LLM 生成结构化结果
-> 解析 reasoningSegments 和 uncertainties
-> BFF 补齐 reviewSummary、riskPoints 和 evidenceItems
-> SSE 流式推送到前端
-> 前端展示审批 Copilot 审查卡、溯源片段和不确定性提示
-> 人工采纳或覆盖后回写 AI 审计
```
# 5 AI 增强与治理体系
## 5.1 AI 审批建议
AI 审批建议的输入边界非常克制：前端不传完整表单和敏感上下文，只传 `approvalId`。BFF 内部读取审批详情、表单摘要、流程轨迹、SLA 状态、代理关系、最近意见、附件摘要和制度上下文，再统一组装 Prompt。
输出统一为结构化结果，包括 `suggestion`、`confidence`、`riskLevel`、`reasoning`、`reasoningSegments`、`uncertainties`、`reviewSummary`、`riskPoints`、`evidenceItems`、`disclaimer`、`generatedAt` 和可选的 `auditEventId`。这样前端渲染不依赖模型自由文本，也便于后续审计和统计。
### 5.1.1 审批 Copilot 审查卡
审批 Copilot 审查卡不是重新做一个通用聊天助手，而是把原来的 AI 建议卡片升级成“可复核的审批审查视图”。它在同一张卡片里聚合四类信息：第一是审批摘要 `reviewSummary`，包括标题、申请人、类型、金额、当前节点和关键时间线；第二是风险点 `riskPoints`，由 BFF 根据高金额、SLA 升级、多次催办、描述缺失、附件缺失等规则确定性生成；第三是依据来源 `evidenceItems`，优先从 `reasoningSegments` 映射出知识库、表单数据、历史数据和模型判断来源；第四才是模型给出的建议、置信度、理由和不确定性。
这个设计的重点是“混合生成”。基础事实和规则风险由 BFF 确定性生成，避免模型把金额、节点、附件等事实编错；AI 继续负责综合判断、理由表达和溯源解释。模型不可用时仍然降级 `manual_review`，但审查摘要、规则风险和兜底依据仍然可以展示，所以用户不会只看到一个失败提示。
面试时可以这样讲：我没有把 AI 做成黑盒按钮，而是把审批上下文、规则风险、制度/表单/历史依据和人工反馈放到同一张 Copilot 审查卡里，让 AI 输出从“建议文本”变成“可解释、可治理、可复核的辅助审查对象”。
## 5.2 Human-in-the-Loop 边界
- AI 只提供建议，不直接触发 `approve / reject / transfer / addSign / remind / withdraw / cancel` 等真实审批动作。
- AI 不参与节点权限、字段权限和角色判断。
- AI 不绕过当前处理人边界，非当前处理人的动作边界不能被 AI 功能绕开。
- 信息不足、模型缺失、解析失败、策略阻断或高风险场景统一倾向 `manual_review`。
## 5.3 Policy-as-Code
Policy-as-Code 用声明式规则定义 AI 能力边界，规则包含作用域、优先级、条件、效果和提示信息。当前策略覆盖超时升级、高金额、代理审批、多次催办、缺少描述等典型风险场景。
- `block`：直接阻断 AI 建议，返回 fallback，不调用 LLM。
- `warn`：允许继续生成建议，但降低置信度，并在前端展示策略警告。
- `allow`：正常生成建议，但仍保留“AI 建议仅供参考，最终以人工审批为准”的免责声明。
这里最重要的设计点是：AI 边界先于模型调用执行，而不是等模型给出结果后再补一句免责声明。
## 5.4 决策审计四维度
AI 审计不只是记录“调用了一次模型”，而是围绕建议生命周期做全链路留痕。
1. 输入上下文：审批 ID、审批类型、金额、风险信号、知识库命中数、Prompt 模板版本。
2. 模型行为：建议结果、置信度、风险等级、理由、模型名、token 用量、延迟。
3. 人工干预：审批人是否采纳、是否覆盖、覆盖原因、实际决策、操作人和时间。
4. 结果影响：最终审批结果、建议是否匹配、策略是否阻断、策略警告列表。
## 5.5 采纳与覆盖反馈闭环
AI 建议展示后，审批人可以采纳建议，也可以覆盖建议。采纳和覆盖都不是前端本地状态，而是回写 BFF 审计服务，形成 AI 建议生成、人工采纳或人工覆盖的生命周期链路。
这套闭环的价值在于面试时可以讲清楚：我不是只做了一个“好看的 AI 卡片”，而是把 AI 建议和真实人工决策关联起来，后续可以统计采纳率、覆盖率、风险分布和平均延迟。
## 5.6 Prompt 模板管理
Prompt 模板不直接硬编码在业务页面里，而是通过模板服务做 CRUD、版本化、激活和在线测试。同一作用域下只有一个 active 模板，其他模板可以处于 draft 或 archived 状态。
模板支持 `{{var}}` 变量替换和 `{{#cond}}...{{/cond}}` 条件块渲染，便于把审批上下文、策略警告、流程摘要、轨迹摘要和表单摘要注入 Prompt。
Prompt 模板有默认 fallback，避免模板缺失时 AI 建议链路整体不可用。这个设计适合回答“Prompt 写死在代码里怎么办”和“Prompt 如何迭代回滚”这类追问。
## 5.7 可解释性溯源
AI 理由不是一段不可拆分的黑盒文本，而是通过 `reasoningSegments` 拆分为四类来源：知识库、表单数据、历史数据、模型判断。
- `knowledge_base`：来源于制度文档、知识库片段和引用条款。
- `form_data`：来源于当前审批单字段、金额、附件摘要和表单数据。
- `historical_data`：来源于历史轨迹、最近审批意见和过往处理过程。
- `model_judgment`：来源于模型综合判断，前端会明确标注这类内容不是制度原文。
## 5.8 不确定性标注
AI 输出中的 `uncertainties` 用于标注需要人工重点核对的问题，例如附件缺失、金额依据不足、制度条款不明确、代理审批语义复杂等。
不确定性标注不会直接改变建议结果，它的作用是提示审批人“哪些点要重点看”。这样既能保留 AI 辅助效率，也不会把不确定判断包装成确定结论。
## 5.9 知识库与 RAG
知识库支持 TXT、Markdown、PDF 三类文档。PDF 文本提取在前端完成，再以 JSON 文本形式提交到 BFF。BFF 负责文档元数据落库、文本分块、Embedding、Qdrant 向量写入和检索召回。
向量链路失败不阻塞文档元数据落库，检索也具备 fallback 能力。这一点非常适合面试时说明“我考虑了外部依赖不可用时的可用性，而不是假设模型和向量库永远正常”。
## 5.10 AI 审计看板
AI 审计看板展示采纳率、置信度分布、风险分布、平均延迟和日志查询，帮助从管理视角观察 AI 建议到底有没有被使用、在哪些场景被覆盖、哪些风险等级最常出现。
这让 AI 能力从“功能点”升级为“可治理对象”：能生成建议、能解释来源、能记录反馈、能统计效果。
# 6 项目亮点
## 6.1 动态表单适配层
第一个亮点是没有把 form-create 直接暴露给业务页面，而是在 `useFormSchemaAdapter` 和动态表单组件之间补了一层协议转换。设计器规则先转换成内部表单协议，再由渲染层消费统一结构。
这样做的价值是隔离第三方规则结构，保证业务页面依赖的是稳定内部协议。未来补字段类型、改校验规则、换表单引擎，主要改适配层，而不是全量改页面。
## 6.2 流程编排与领域模型双向映射
第二个亮点是把 LogicFlow 图数据和审批执行模型拆开。画布数据负责“能编辑、能拖拽、能回显”，审批领域模型负责“能执行、能流转、能治理”。
保存时存的是业务定义，编辑时用的是图形结构，回显时再把定义转换为图数据。这避免把审批协议绑死在图库结构上。
## 6.3 审批自动治理与闭环一致性
第三个亮点是审批闭环不是只做到“能提交、能处理”，而是补上了任务模型、代理审批、SLA 自动升级、会签或签策略、轨迹、通知和统计一致性。
这个亮点最容易打动面试官的地方在于，它直接回答了复杂审批系统最容易混乱的问题：为什么待办归属、详情权限、轨迹记录和统计口径能对得上。
## 6.4 流程治理与审计追溯
第四个亮点是把流程平台能力进一步做到了治理层。流程定义不是一次性配置，而是带版本、带发布、带回滚、带影响分析的治理对象。
关键动作都统一进入审计模型，能解释是谁在什么时间做了什么调整，并且可以追溯到前后变化。这让系统不只是能配置流程，还能治理流程。
## 6.5 AI 增强与治理闭环
第五个亮点是 AI 不只是一个建议卡片，而是被升级成审批 Copilot 审查卡：它把审批摘要、规则风险点、依据来源、AI 建议、推理溯源、不确定性和采纳/覆盖反馈放在同一条辅助审查链路里。
Policy-as-Code 控制 AI 能不能给建议，BFF 确定性生成高金额、SLA 升级、多次催办、描述缺失和附件缺失等风险点，AI 审计记录建议生命周期，Prompt 模板让提示词可管理，推理溯源解释建议依据，不确定性标注提醒人工核对。这样 AI 能力既能增强审批效率，又不会越过责任边界。
# 7 表单类型、角色与权限设计
## 7.1 表单类型划分
在该审批项目中，前端接入的核心审批表单主要分为三类。
1. 假勤类单据：如请假、出差、加班，通常涉及时间区间、请假类型、证明材料和销假补录等字段，联动规则较多。
2. 费用类单据：如报销、借款、付款申请，通常包含金额、明细、附件、预算校验和财务核验字段，流程链路较长。
3. 采购与行政类单据：如采购申请、合同审批、用印申请，更强调节点流转、附件查看和跨部门协作。
从当前实现来看，审批主链路可以承载 `leave`、`expense`、`purchase` 三类表单，并且能够在审批详情页根据单据类型自动解析对应表单协议和流程定义。
这意味着前端不是为每一类单据单独维护一套页面，而是把表单类型抽象成“表单 Schema + 流程定义 + 节点权限”的协议组合，再由运行时动态渲染。
## 7.2 角色语义与前端实现边界
从业务语义上看，审批参与方通常包括发起人、直属主管、部门负责人、财务、HR、行政以及流程管理员等。这些角色决定了流程在组织层面的责任分工，比如谁发起、谁审核、谁复核、谁归档。
但在前端实现里，真正决定页面展示和交互权限的，并不只是“用户属于哪个角色”，而是“当前流程走到哪个节点、当前任务实际归谁处理”。
同一个用户在不同流程、不同节点下，能够看到的字段、能够执行的操作、是否拥有处理权限，都可能完全不同。因此前端并没有为“主管页面”“财务页面”“HR 页面”分别维护独立视图，而是以“当前节点 + 当前任务处理人 + 节点权限配置”作为运行时判断依据。
AI 建议与制度知识库则位于辅助层，只为当前处理人提供参考，不参与角色判定本身，也不具备越过节点权限边界的能力。
## 7.3 权限模型设计
这个项目的权限设计不是停留在菜单权限和数据权限，而是进一步下沉到了节点权限和字段权限。
1. 菜单权限：决定用户能否进入审批相关模块，例如待办、已办、抄送、代理设置、AI 审计看板和 Prompt 模板管理等页面。
2. 数据权限：决定用户能查看哪些审批单据，例如“我发起的”“待我处理的”“抄送给我的”。
3. 节点权限：决定当前用户在当前节点是否可以执行审批、转交、加签、催办、撤回、取消等动作。
4. 字段权限：决定当前节点下某个字段是 `editable`、`readonly`、`hidden` 还是 `required`。
动态表单本身同时支持两类控制来源。一类是字段自身的联动规则，例如 `requiredWhen`、`visibleWhen`、`disabledWhen`，用于解决字段之间的条件依赖；另一类是节点权限映射，用于解决流程上下文驱动的只读、隐藏和必填要求。
也就是说，字段联动回答的是“表单内部条件成立时字段怎么变”，节点权限回答的是“流程走到当前节点时字段应该怎么变”。
## 7.4 当前项目中的权限落地方式
在审批详情页，前端会先根据审批记录解析出当前单据对应的表单协议，再解析当前节点、当前节点任务和节点权限，然后把这些信息一起交给动态表单组件。
动态表单内部先基于 Schema 生成基础规则，再结合节点权限做一次权限变异，如果当前页是只读态，还会统一给字段补上 `disabled` 或 `readonly` 属性。
这意味着权限不是写死在页面模板里，而是通过“基础表单协议 + 节点权限映射 + 运行时状态”三者组合得到最终渲染结果。
在审批待办场景里，列表过滤也不是按申请人或组织角色，而是按当前任务处理人过滤。这样在代理审批、转交审批、SLA 自动升级这些场景下，待办归属才会和详情权限保持一致。
## 7.5 典型案例一：报销单
报销单是一个典型的跨节点联动场景，也是最能体现“同一张单据，不同节点表现不同”的类型。
在发起节点，用户通常需要填写报销事由、报销金额、费用明细、发生日期、附件等基础信息，这一阶段以录入和校验为主，大部分字段处于可编辑状态。
当流程流转到直属主管节点后，表单的核心目标已经不是继续填单，而是让主管进行合理性审核。因此前端会把大部分申请字段切换为只读，只保留审批意见、审批动作和必要的上下文信息。
进入财务节点后，单据又会进入另一种语义环境。此时前端可能需要额外展示发票核验、预算校验、付款方式、财务备注等字段；其中部分字段会动态显示，部分字段会变为必填，而申请人原始填写的信息则继续保持只读。
整个过程中，前端始终渲染的是同一份报销单 Schema，但由于当前节点变化，字段的展示状态、编辑权限和校验要求随之变化，这正是跨节点联动的典型体现。
如果面试官追问这套能力前端是怎么做到的，可以回答：我没有为主管审批页、财务审批页分别写独立页面，而是通过节点权限映射控制字段在运行时切换为 `editable / readonly / hidden / required`，让同一张单据在不同审批节点下生成不同视图。
## 7.6 典型案例二：请假单
请假单同时体现了跨字段联动和跨节点联动两类能力，非常适合作为面试里的例子。
发起阶段，员工需要填写请假类型、请假时间、请假天数、请假原因和证明材料等信息。这一阶段的重点不是节点权限，而是字段之间的业务依赖关系。
例如当请假类型选择“病假”时，证明材料字段需要自动显示并变为必填；如果选择其他类型，这个字段则可以隐藏或降级为非必填。这个变化不是由流程节点触发的，而是由表单内部字段值触发的，属于跨字段联动。
随后当流程进入主管审批节点后，前端会把申请人原始填写的信息整体切换为只读，只保留审批意见和审批动作等入口。进入 HR 节点后，又可能额外出现 HR 审核意见、假期余额确认、销假补录等字段，同时部分历史字段继续保持只读。
如果面试官继续追问这两类联动有什么本质区别，可以回答：跨字段联动解决的是表单内部条件依赖，比如 A 字段的值影响 B 字段的显示和校验；跨节点联动解决的是流程上下文变化，比如同一张表单在发起、主管审批、HR 审核阶段呈现不同的字段权限和操作态。
## 7.7 权限设计总结
这一类审批系统真正难的，不是表单字段多，也不是流程节点多，而是如何在不复制页面的前提下，让同一张单据随着流程状态变化自动切换视图。
这个项目的核心设计思路是：表单负责承载业务字段，流程负责承载节点上下文，权限模型负责把两者在运行时连接起来。角色是业务语义，节点是渲染依据，字段权限是最终落点。
AI 建议和制度知识库位于辅助层，只为当前处理人提供解释、风险提示和制度依据，不改变真实审批边界。
# 8 高频面试 QA
## 8.1 第一维度：动态表单与协议适配
### 8.1.1 Q1：为什么选 form-create，而不是自己手写一套 JSON 表单解析器？
回答：我更看重的是成熟的渲染、校验和规则承载能力，而不是单纯把组件映射出来。自己写一套简单解析器不难，但一旦涉及字段校验、联动规则、只读禁用、运行时权限注入和后续扩展，维护成本会迅速失控；用 form-create 可以把精力集中在内部表单协议、适配层和平台化规则承载上。
追问：那你在这个项目里真正自己做了什么？
补充回答：我没有把 form-create 直接暴露给业务页面，而是在 `useFormSchemaAdapter` 和动态表单组件之间补了一层协议转换和权限变异。这一层负责协议隔离、组件映射、规则标准化和节点态权限注入，这部分才是项目里的核心实现。
### 8.1.2 Q2：如果设计器规则、后端数据结构和运行时表单格式不一致，你怎么处理？
回答：我用的是适配器模式。先把设计器规则统一转换成内部表单协议，再把 required、pattern、range、min / max 这类校验规则标准化，最后由渲染层消费统一协议。这样第三方规则结构、后端数据结构和前端运行时格式就被适配层隔离开了。
追问：这样做最大的价值是什么？
补充回答：最大的价值是协议稳定。以后换表单引擎、补字段类型、加校验规则，主要改适配层和渲染层，不需要全量改业务页面。对平台型项目来说，协议隔离比库本身更重要。
### 8.1.3 Q3：如果某个审批节点要把一半字段变只读，另一半字段隐藏，你怎么做？
回答：我不会去改原始 Schema，而是在运行时做节点态注入。动态表单先拿基础规则，再结合当前节点权限做一次规则变异；如果页面是只读态，还会统一给字段补 `disabled / readonly`，这样同一份表单协议就可以适配不同审批节点。
追问：这样会不会污染原始规则？
补充回答：不会，运行时处理的是派生后的规则结构，不是直接回写原始协议，所以可以做到对原始 Schema 零侵入。这也是“运行时权限注入”而不是“配置写死”的关键区别。
## 8.2 第二维度：流程编排与流表联动
### 8.2.1 Q4：为什么选 LogicFlow，而不是直接自己维护节点数组，或者用别的图库？
回答：因为这个项目需要的不只是“能画图”，还要支持拖拽、节点编辑、连线事件、只读预览和流程定义回填。LogicFlow 在流程编排场景里更贴业务，输出也是相对容易处理的 JSON 结构，和 Vue 组件集成成本也可控。
追问：你在这个项目里最看重它哪一点？
补充回答：我最看重的是它和业务定义之间比较容易做双向映射。也就是画布交互模型和审批执行模型可以拆开，前者负责“可编辑”，后者负责“可执行”，不会把审批协议绑死在图库结构上。
### 8.2.2 Q5：流程图数据怎么保证“能编辑、能保存、还能稳定回显”？
回答：我把流程定义作为业务领域模型，把 LogicFlow 图数据作为编辑模型，分别做了 `definition -> graph` 和 `graph -> definition` 两个方向的转换。这样保存时存的是业务定义，编辑时用的是图形结构，回显时再做一次映射，画布只是交互壳子。
追问：为什么不直接把 LogicFlow 原始数据存起来？
补充回答：因为原始图数据更偏渲染和交互，不适合直接作为审批执行协议。审批真正关心的是节点类型、处理人、条件、权限和超时配置，这些应该沉淀在业务定义层，而不是图库结构里。
### 8.2.3 Q6：表单和流程是怎么打通的？同一张单据为什么能在不同节点呈现不同形态？
回答：流程节点是主状态，表单 Schema 是客状态。进入详情页后，我会先解析当前节点、任务进度和节点权限，再把这些信息传给动态表单层，让它决定字段的读写、隐显和按钮态；所以同一张单据在发起、审批、财务这些节点下，看到的是不同的交互视图。
追问：这和普通的 RBAC 权限有什么区别？
补充回答：这里不是菜单权限，而是节点上下文驱动的字段权限。真正决定页面能不能操作的，不只是用户角色，还有当前流程走到哪个节点、当前处理人是谁，所以它是运行时映射，不是角色写死。
## 8.3 第三维度：审批闭环与自动治理
### 8.3.1 Q7：你们的会签和或签是怎么实现的？
回答：我在审批任务里保留了当前节点任务集合和节点模式。`or` 模式下，一个人通过就自动关闭其他待处理任务；`and` 模式下，所有人都通过节点才结束，同时驳回逻辑也按模式分别处理，所以进度、状态、通知和轨迹都是跟着节点策略一起算的。
追问：为什么这块不能只看审批单状态？
补充回答：因为审批单状态是结果，真正决定流程怎么走的是当前节点任务集合和处理进度。如果没有任务层，协同审批、加签、自动关闭剩余任务这些场景都很难准确表达，所以这里的核心是任务模型。
### 8.3.2 Q8：代理审批和 SLA 自动升级分别是什么？为什么要拆开做？
回答：代理审批是“人不在时，别人代我处理”，SLA 自动升级是“超过时效没人处理，系统自动改派”。我在任务模型里拆了 owner 和 handler 两层身份，owner 表示责任归属，handler 表示当前实际处理人，这样代理、升级、待办归属和详情权限才能统一解释。
追问：如果升级和代理同时存在，顺序怎么定？
补充回答：我这里定的是先升级、再代理。也就是先确定任务升级后归谁，再判断新的责任人有没有代理规则，这样责任归属和实际处理人都能解释得通，状态口径也更稳定。
### 8.3.3 Q9：审批后为什么待办、详情、统计、通知能保持一致？
回答：我把审批相关自动治理统一收口在审批域 API 层，每次查列表、查详情、处理审批、查统计、查通知时都会先跑自动治理，再通过 Vue Query 的 `invalidateQueries` 触发列表、详情、统计和通知的失效刷新。这样所有页面走的是同一套数据源，而不是各自维护一份状态。
追问：这里最大的收益是什么？
补充回答：最大的收益是状态一致性。用户处理完审批后，不需要手动刷新多个页面，待办归属、详情轨迹、工作台统计和通知提醒会一起更新，不容易出现页面之间数据打架。
### 8.3.4 Q10：你觉得这个项目最值得讲的技术价值是什么？
回答：不是单独某个库选得多漂亮，而是我把动态表单、流程编排、审批治理和 AI 辅助串成了一条完整链路。前端既承担了协议适配，也承担了节点态渲染、任务状态承载、审批闭环治理和 AI 交互承载，所以这个项目能讲的不只是页面开发，而是一个前端主导的平台型审批项目。
追问：如果面试官继续深挖，你最建议往哪两个点展开？
补充回答：我会优先展开两个点。第一是动态表单适配层，讲协议隔离和运行时权限注入；第二是审批闭环，讲会签或签、代理审批、SLA 自动升级以及状态一致性。AI 可以作为第三个补充亮点，但不建议一开始就把它当主叙事。
## 8.4 第四维度：流程治理、审计追溯与 AI 边界
### 8.4.1 Q11：流程版本治理和审计链路你是怎么一起设计的？
回答：我采用了全快照式版本策略，每次创建、更新、发布、回滚都生成完整快照。版本列表展示版本号、操作人、时间、状态、备注，发布前提供影响分析，回滚时支持版本可选 + 风险提示 + 二次确认。同时我把这些关键动作统一接入 AuditEvent 模型，写入操作人、动作、模块、结果、before / after 快照、TraceId、IP、UA、耗时和关联链接，形成从治理动作到追溯证据的完整链路。
追问：为什么用全快照而不是增量 diff？
补充回答：全快照保证了回滚的原子性和可验证性，实现简单，适合 MVP 阶段。增量 diff 在当前 demo 项目里复杂度更高，且对演示价值和交付效率的收益不明显。
### 8.4.2 Q12：AI 审批建议为什么只做辅助，不直接驱动审批动作？
回答：因为审批系统的核心风险在于责任归属和决策可追溯，AI 可以帮助提升判断效率，但不能替代真实审批人。我这里采用的是 Human-in-the-Loop 设计：前端只传 `approvalId`，BFF 内部读取审批上下文并裁剪敏感信息，统一返回结构化结果，包括建议、置信度、风险等级、审查摘要、风险点、依据来源、推理溯源和不确定性；如果模型缺失、解析失败或信息不足，就统一降级到 `manual_review`。
追问：这样设计最大的价值是什么？
补充回答：最大的价值是把“智能能力”和“真实动作”明确分层。AI 可以提升效率，但不会绕过节点权限、角色边界和审计链路，系统因此仍然保持可控、可解释和可回退。
## 8.5 第五维度：AI 治理新增追问
### 8.5.1 Q13：AI 的能力边界怎么控制？
回答：我没有只靠文案提示“AI 仅供参考”，而是在 BFF 层做了 Policy-as-Code。策略规则会在模型调用前执行，命中 `block` 直接返回 fallback，不调用 LLM；命中 `warn` 才继续生成建议，但会降低置信度并展示警告。
追问：为什么 block 规则不能调用 LLM？
补充回答：因为 block 表示当前场景本身不适合 AI 介入，比如超时升级这类紧急责任场景。既然已经确定不能让 AI 给建议，就不应该再调用模型，否则会产生“虽然阻断但其实模型判断过”的审计歧义。
### 8.5.2 Q14：AI 决策怎么追溯？
回答：AI 建议生成后会写入审计，采纳和覆盖也会写入审计。审计不是只记录一行日志，而是围绕输入上下文、模型行为、人工干预、结果影响四个维度留痕。这样后续能解释模型基于什么信息给建议，审批人是否接受，最终决策和 AI 是否一致。
追问：这和普通操作日志有什么区别？
补充回答：普通操作日志只回答“谁做了什么”，AI 审计还要回答“模型看到了什么、输出了什么、人工怎么处理、对最终结果有没有影响”。
### 8.5.3 Q15：Prompt 为什么不能直接写死在代码里？
回答：Prompt 会随着业务规则、风险口径和模型表现不断调整，如果写死在代码里，每次修改都要发版，也无法管理版本和回滚。我这里把 Prompt 做成模板管理，支持 CRUD、版本化、变量渲染、激活和在线测试。
追问：模板缺失怎么办？
补充回答：系统保留默认 fallback 模板，保证模板缺失时审批建议链路不会整体不可用。同时 active 模板按 scope 生效，避免多个模板同时影响同一类 AI 能力。
### 8.5.4 Q16：AI 给出的建议凭什么可信？
回答：我不把可信建立在“模型一定对”上，而是通过结构化输出、引用溯源和不确定性标注降低黑盒感。推理理由会拆成知识库、表单数据、历史数据和模型判断四类来源，前端可以展示每段理由的来源和置信度。
追问：如果 AI 自己也不确定怎么办？
补充回答：不确定点会单独进入 `uncertainties`，提醒审批人重点核对。它不会替代审批动作，也不会强行把不确定判断包装成确定结论。
### 8.5.5 Q17：知识库和 AI 审批建议是什么关系？
回答：我把知识库理解成制度依据层，把 AI 建议理解成辅助判断层。知识库负责提供制度条款、文档片段和引用来源，AI 建议则在审批上下文、轨迹信息和制度依据基础上生成结构化辅助意见。两者配合之后，系统更像“带依据的辅助审查”，而不是“黑盒自动审批”。
追问：向量库或模型不可用怎么办？
补充回答：向量写入失败不阻塞文档元数据落库，检索有本地 fallback；模型不可用时审批建议统一降级到 `manual_review`，不影响审批主链路。
### 8.5.6 Q18：AI 审计看板有什么价值？
回答：AI 审计看板把建议采纳率、覆盖率、置信度分布、风险分布和平均延迟展示出来，让 AI 能力从“功能点”变成“可治理对象”。面试时可以讲，它不仅能生成建议，还能评估建议是否被业务接受，以及在哪些场景容易被人工覆盖。
### 8.5.7 Q19：审批 Copilot 审查卡和普通 AI 建议卡有什么区别？
回答：普通 AI 建议卡通常只展示模型给出的建议和理由，容易变成“一个文本按钮”。我这次做的审批 Copilot 审查卡更强调业务审查视图：BFF 先确定性生成审批摘要和规则风险点，再把模型输出的推理溯源映射成依据来源，最后把建议、置信度、不确定性和采纳/覆盖反馈一起展示。这样审批人看到的不是一句“建议通过”，而是“这张单是什么、风险在哪、依据来自哪里、哪些点需要人工核对、最终是否采纳 AI”。
追问：为什么不让这些内容全部由 AI 生成？
补充回答：因为审批里的标题、金额、节点、附件、催办次数这类基础事实不能依赖模型自由发挥，所以我采用混合生成。事实摘要和规则风险由 BFF 根据审批上下文确定性生成，AI 负责综合判断和理由表达；模型异常时仍然降级 `manual_review`，但摘要、风险点和兜底依据仍然可用。
# 9 复习时的表达建议
## 9.1 讲述主线
讲这个项目时，顺序最好固定成“平台抽象 -> 审批闭环 -> 流程治理 -> AI 增强 -> AI 边界”。不要一上来就堆 Ark、Qdrant、RAG 这些名词，面试官更想听的是你为什么要把审批系统做成协议驱动的引擎化平台，这样解决了什么复杂度问题。
## 9.2 面向业务面试官
如果面试官偏业务视角，就多讲审批闭环、一致性、制度复核和风险控制。重点讲为什么待办归属、详情权限、轨迹记录和统计口径能对得上，以及 AI 为什么只辅助不替代审批人。
## 9.3 面向技术面试官
如果面试官偏技术视角，就多讲协议适配、领域模型、共享契约、自动治理、运行时权限注入和 AI 治理。重点讲你如何把第三方表单规则、流程画布模型、审批执行模型和 AI 结构化结果隔离开。
